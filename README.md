## 왜 만드나

임베디드에서 제일 비싼 버그는 **컴파일도 되고 업로드도 되는 버그**입니다.

```c
// config.h
#define LED_PIN 34

// main.cpp
pinMode(LED_PIN, OUTPUT);   // 컴파일 통과. 업로드 성공. LED는 안 켜짐.
```

구형 ESP32의 GPIO34는 입력 전용입니다. 컴파일러는 모르고, 회로도 DRC도 모릅니다.
문제가 **코드와 회로도 사이**에 있기 때문입니다. 아무 도구도 그 사이를 보지 않습니다.

발견되는 시점은 보드가 도착해서 안 켜질 때입니다. 원인 추적에 반나절,
설계 수정 후 재발주까지 2~4주가 걸립니다.
([Lifecycle Insights](https://www.cadstrom.io/resources/the-hidden-cost-of-pcb-respins-why-90-of-first-prototypes-fail):
프로젝트당 평균 2.9회 리스핀, 회당 일정 영향 8.5일)

금지된 핀은 칩마다 다릅니다. ESP32-C6에는 입력 전용 핀이 아예 없는 대신
플래시 핀(GPIO24~30)과 스트래핑 핀(GPIO4·5·8·9·15)이 있습니다.
그래서 규칙에 핀 번호를 적지 않고 [`docs/CHIPS.md`](./docs/CHIPS.md)의 칩별 표를 참조합니다.

## 무엇을 하나

세 가지 자료를 동시에 읽고 대조합니다.

```
넷리스트 (IPC-D-356)  ─┐
펌웨어 소스 (C/C++)    ─┼→  규칙 엔진  →  발견 + 근거 + 수정 제안
부품 데이터시트 (PDF)  ─┘
```

**예시 검출**

```
[치명] R07  코드가 쓰는 핀이 회로도에 미연결
  회로도  U1.GPIO4 → (미연결)
  코드    src/main.cpp:44  pinMode(LED_PIN, OUTPUT)   // LED_PIN = 4 (config.h:8)
  제안    GPIO4 배선을 추가하거나 코드에서 이 핀 사용을 제거하세요
```

## 기존 도구와의 차이

| | 회로도 | 기존 펌웨어 검증 | 실물 보드 |
|---|:---:|:---:|:---:|
| STM32CubeMX, esp32pin.com | 규칙 표만 제공 | ✕ | 불필요 |
| Traceformer, Flux Design Review | ✅ | **✕ 명시적 제외** | 불필요 |
| Embedder | 코드 생성 입력용 | ✕ (생성이지 검증 아님) | **필요** |
| **Prefab** | ✅ | **✅** | 불필요 |

회로도만 보는 도구는 이미 있습니다. **코드까지 함께 보는 도구가 없습니다.**

## 설계 원칙

> **토폴로지가 질문을 던지고, 데이터시트가 답한다.**

1. **판정은 결정적 코드가 한다.** 규칙 함수는 순수 함수이고 LLM을 호출하지 않습니다.
   같은 입력이면 항상 같은 결과가 나옵니다.
2. **LLM은 비정형 문서를 읽는 데만 쓴다.** 데이터시트 PDF에서 값을 뽑아 JSON 스키마로
   반환하는 것까지가 LLM의 역할입니다.
3. **모르면 `UNRESOLVED`.** 부품을 식별하지 못하면 추측하지 않고 판정을 보류합니다.
4. **못 한 일을 숨기지 않는다.** BOM이 없어 못 돌린 규칙은 응답에 `skipped`로 실립니다.
5. **칩을 하드코딩하지 않는다.** 핀 번호는 규칙이 아니라 칩 표에 있습니다.
   해당 없는 칩에서는 "이상 없음"이 아니라 `skipped`로 나갑니다.

## 시작하기

### 요구사항

- Python 3.11+
- Node 20+, pnpm
- (선택) Docker

### 백엔드

```bash
cd apps/api
uv sync                      # 또는 pip install -e ".[dev]"
pytest -q

# 실제 보드로 검사 실행
python -m prefab tests/fixtures/esp32-c6-presence-smart-light.d356

# 개발 서버
uvicorn web.app:app --reload --port 8000
```

### 프론트엔드

```bash
cd apps/web
pnpm install
cp .env.example .env         # VITE_API_BASE=http://localhost:8000
pnpm dev                     # http://localhost:5173
```

`VITE_API_BASE`가 비어 있으면 `src/mocks/check.json`으로 동작합니다.
백엔드 없이 화면 작업이 가능합니다.
목 데이터는 실제 보드를 파서와 규칙 엔진에 돌려 얻은 값입니다. 손으로 적은 숫자가 없습니다.

## 규칙 카탈로그

`기본`은 기존 상용 도구가 이미 제공하는 범위, `차별`은 Prefab만 하는 것입니다.

| ID | 규칙 | 등급 | 필요 입력 | 상태 |
|---|---|:---:|---|:---:|
| R01 | 코드가 이 칩에서 쓸 수 없는 핀을 사용 | 차별 | netlist, firmware | ✅ |
| R02 | 회로도가 SPI 플래시 전용 핀에 배선 | 기본 | netlist | ✅ |
| R03 | 스트래핑 핀이 전원·접지에 직결 | 기본 | netlist | ✅ |
| R04 | 외부 부품 출력이 GPIO 입력 최대 정격 초과 | 기본 | netlist, bom | ✅ |
| R05 | 이 칩이 지원하지 않는 주변장치 조합 | 차별 | netlist, firmware | ✅ |
| R07 | 코드가 쓰는 핀이 회로도에 미연결 | 차별 | netlist, firmware | ✅ |
| R08 | 회로도에 연결됐는데 코드가 초기화 안 함 | 차별 | netlist, firmware | ✅ |
| R09 | 부팅 시 출력 나오는 핀에 부하 연결 | 기본 | netlist | ✅ |
| R10 | 회로도 변경 후 코드 미추종 (드리프트) | 차별 | netlist, firmware (+이전 넷리스트) | ✅ |
| R11 | 네트명이 주장하는 전압 ≠ 소스 부품 전원 도메인 | 기본 | netlist | ✅ |
| R12 | 상위 전원 도메인이 하위를 직결 | 기본 | netlist | ✅ |
| **R14** | **같은 이름의 핀 상수가 서로 다른 핀을 가리킴** | 차별 | firmware | ✅ |
| **R15** | **MCU 출력 하이가 상대 부품의 입력 문턱에 못 미침** | 차별 | netlist, firmware | ✅ |

**카탈로그 13개 · 구현 13개.** 개수의 유일한 진실은
[`catalog.py`](./apps/api/src/prefab/catalog.py) 이고, 표가 어긋나면 테스트가 막습니다.

폐기한 두 개도 남겨 둡니다 — **번호를 재사용하지 않기 위해서입니다.**

- **R6** I2C 풀업 누락 — Flux Design Review 가 이미 제공합니다
- **R13** 코드가 출력으로 구동하는 핀에 다른 출력이 연결 — 하드웨어 담당 판정이
  "문제 안 됨" 이었습니다. **구현하기 전에 기각된 규칙입니다.**

**R14 와 R15 는 상상해서 만든 규칙이 아닙니다.** 둘 다 실제로 일어난 사고를 보고
뒤늦게 만들었습니다 — R14 는 [남의 오픈소스 보드에서](#llm-규칙-발견자),
**R15 는 우리 보드에서.**

R15 는 8/21 에 하드웨어 담당이 보고한 증상에서 나왔습니다 —
*"LED가 ON은 되는데 OFF가 안되는 게 문제야."* 3.3V MCU 가 5V 릴레이 모듈의
액티브 로우 입력을 모는데, 끄려고 내는 3.3V 가 하이로 읽히지 않는 모양입니다.

**카탈로그에 이 방향이 통째로 없었습니다.**

| | 방향 | 결과 |
|---|---|---|
| R04 | **들어오는** 쪽 — 외부 출력이 GPIO 정격을 넘는가 | 보드가 망가진다 |
| R15 | **나가는** 쪽 — MCU 출력이 상대 입력 문턱에 닿는가 | 안 망가지는데 **안 돈다** |

**R1·R5는 칩마다 검사 내용이 다릅니다.** 구형 ESP32에서는 입력 전용 핀과 ADC2/WiFi 충돌을,
ESP32-C6에서는 플래시 핀과 스트래핑 핀 사용을 봅니다. 해당 항목이 없는 칩에서는
"이상 없음"이 아니라 `skipped`로 나갑니다. 표는 [`docs/CHIPS.md`](./docs/CHIPS.md)에 있습니다.

**R7·R8·R10은 칩과 무관합니다.** 코드가 참조하는 핀과 넷리스트의 연결을 비교할 뿐입니다.
차별 등급의 중심은 이쪽입니다.

### 규칙 추가하기

```python
# apps/api/src/prefab/rules/r07_pin_not_connected.py
RULE_ID  = "R07"
TITLE    = "코드가 쓰는 핀이 회로도에 미연결"
SEVERITY = Severity.CRITICAL
TIER     = "차별"
NEEDS    = ["netlist", "firmware"]

def check(ctx) -> list[Finding]:
    """순수 함수. 네트워크·LLM·파일 IO 금지. 핀 번호는 ctx.chip 에서 가져온다."""
    ...
```

규칙 하나당 테스트 3개가 필수입니다 — **양성 / 음성 / 미해결**.
칩별로 갈리는 규칙은 **칩마다** 세 개씩 둡니다.

실제 보드 픽스처에 새 경고가 뜨면 발견인지 오탐인지 확인하고, 오탐이면 음성 테스트로 고정합니다.
`.claude/skills/prefab-rule` 스킬을 쓰면 이 절차를 자동으로 따릅니다.

## 프로젝트 성과

### 1. 만들려던 것을 만들었고, 배포까지 했습니다

```
화면  https://prefab-web.onrender.com
API   https://pnuai-c-06-eece-prefab.onrender.com
```

넷리스트를 올리면 검사가 돌고 근거가 붙은 리포트가 나옵니다.
**부품 사실 3건이 서버에 심겨 있어 데이터시트 해제도 배포판에서 실제로 돕니다** —
영구 디스크 없이 무료 플랜으로 돌립니다.

배포된 화면에서 실측 보드를 올린 결과입니다.

```
치명 2 · 경고 1 · 해제됨 2 · 실행한 규칙 12/12

[치명] R07  코드가 D10(GPIO18)을 출력으로 구동하는데 회로도에서 미연결
       회로도  U1.D10 (GPIO18, 패드명 D10_) → N/C
       코드    smart_shoe_cabinet_v1.ino:16  const int LED_PIN = D10;
               smart_shoe_cabinet_v1.ino:31  digitalWrite(LED_PIN, LOW);
       제안    D10 에 배선을 추가하거나 코드에서 LED_PIN 사용을 지우세요
```

**해제 2건**이 중요합니다. 경고를 낸 것이 아니라 **데이터시트 근거로 지운 것**입니다.
경고만 쌓는 도구는 3일이면 꺼집니다.

### 2. 검증을 했고, 그 숫자가 못 재는 것까지 적었습니다

```
검출  17/17 (100%)
오탐  결함 없는 케이스 14개 중 0개에서 발생 (0%)

이 숫자가 재는 것 : 케이스 27개 (합성 25 · 실측 2)
이 숫자가 못 재는 것 : 남의 보드에서의 재현율.
   공개 저장소는 작동하는 보드만 올라와서 라벨된 결함이 안 남는다
   (커밋 5,299건을 훑어 핀이 바뀐 커밋 2건). 실측 케이스는 2개뿐이고
   나머지는 우리가 만들었다 — 외부 검증이 아니라 회귀 방지에 가깝다.
```

이 마지막 문단은 **측정 도구가 스스로 출력합니다.** 숫자만 떼어 인용되는 것을
막기 위해 코드에 넣었습니다.

### 3. 실제 결함을 남의 보드에서 찾았고, 그것이 규칙이 됐습니다

`FForzano/xgsail-e1` (Apache-2.0)에서 실제로 일어난 일입니다.

```
회로도            /TFT_BL     → GPIO19
                 /VSPI_MISO  → GPIO25

User_Setup.h:15  #define TFT_BL     19   // Swapped with MISO to match soldered E1 wiring
config.h:22      #define TFT_BL_PIN 25   ← 옛 값 그대로
edge.ino:265     ledcAttach(TFT_BL_PIN, ...);
```

배선이 바뀌어 백라이트가 GPIO19 로 갔고, 개발자가 `User_Setup.h` 는 고치면서
**주석까지 남겼는데 `config.h` 가 안 따라왔습니다.** 코드는 지금 SPI MISO 선에
PWM 을 걸고 있습니다.

**이것이 우리가 만들려던 문제의 실물입니다.** "회로도가 바뀌었는데 코드가 안 따라온다" 를
남의 저장소에서 실제로 찾았습니다. 여기서 **R14** 가 나왔습니다.

### 4. 우리 보드에서 난 결함이 규칙이 됐습니다

8/21, 하드웨어 담당의 보고 — *"지금 LED가 ON은 되는데 OFF가 안되는 게 문제야."*

3.3V MCU 가 5V 릴레이 모듈의 액티브 로우 입력을 몹니다. 끄려고 3.3V 를 내는데,
모듈 입력단이 5V 기준이면 그게 하이로 안 읽힙니다.

**우리 카탈로그에 이 방향이 통째로 없었습니다.** R04 는 *들어오는* 쪽(보드가
망가진다)만 봤고, *나가는* 쪽(안 망가지는데 안 돈다)은 아무도 안 봤습니다.
그래서 **R15** 를 만들었습니다.

```
[CRITICAL] R15  net: _IN_ACTIVE_LOW
  코드가 U1.D5를 출력으로 몹니다. 이 핀은 5V 로 도는 K1 의 K1.pad- 에 이어져 있는데,
  K1이 이 핀을 입력으로 받는다면 MCU 가 낼 수 있는 3.3V 가 하이로 읽히는지
  확인해야 합니다.
  ! JQC-3FF-S-Z 의 입력 하이 문턱(Vih)이 필요합니다
```

**`UNRESOLVED` 입니다.** 문턱값을 모르므로 "이것이 원인이다" 라고 적지 않습니다.
핀 방향도 넷리스트에 없어서 *"받는다면"* 이라고 조건절로 씁니다.

이 규칙이 일주일 전에 있었다면 **보드를 만들기 전에 이 자리를 짚었을 것입니다.**
그게 이 제품이 하려는 일 그대로입니다.

### 4-1. 그리고 그 규칙이 고쳐지는 것까지 봤습니다

R15 를 만든 그날, 하드웨어 담당이 **2N3904 트랜지스터 레벨시프트**로 회로를
고쳤습니다 (REV2). 같은 도구를 다시 돌렸습니다.

```
REV1 (D5 → 릴레이 IN 직결)      치명 R15 · 치명 R04
REV2 (D5 → 1kΩ → 2N3904 → IN)   발견 1건, 그마저 해제됨
```

**도구가 짚는다 → 사람이 고친다 → 도구가 조용해진다.** 그 고리가 실제로 한 바퀴 돌았고,
`tests/test_rev2_transistor_fix.py` 가 그 사실을 붙잡고 있습니다.

한 가지가 더 나왔습니다. `io_level: 5V` 를 실측으로 넣자 **한때 해제됐던 경고가
치명으로 되돌아왔습니다.** 그 네트는 8/19 에 저항 측정으로 해제된 자리였고,
그때 사실 파일에 *"저항계는 트랜지스터·다이오드 경로를 못 본다"* 고 적어 두었습니다.
**적어둔 한계가 그대로 왔습니다.**

앞의 측정이 틀렸던 것이 아닙니다 — **좁았을 뿐입니다.** 사실이 늘면 판정이 바뀌고,
한 번 지운 것도 되살아납니다. 그러지 못하면 그건 파이프라인이 아니라 예외 목록입니다.

> **PCB(REV1)는 이미 발주된 뒤였습니다.** 그래서 REV2 는 손으로 개조해야 합니다.
> 발주 전에 이걸 잡는 것이 이 제품이 하려는 일 그대로입니다.

### 5. 하드웨어가 규칙을 기각한 두 번

소프트웨어만 있는 팀이었으면 둘 다 오탐으로 출하됐을 것입니다.

- **R13** (출력끼리 충돌) — 구현 **전에** 기각됐습니다. 하드웨어 담당 판정이
  "문제 안 됨" 이었습니다. 안 만든 것이 성과입니다.
- **`_IN_ACTIVE_LOW` 의 R12** — 릴레이 모듈을 보드에서 뽑아 `IN`↔`VCC` 를
  20kΩ·2MΩ 범위로 측정했고 둘 다 `OL` 이었습니다. 5V 가 올라올 경로가 없으므로
  **오탐이었습니다.** `parts/jqc-3ff-s-z.json` 에 실측값으로 기록해 자동 해제됩니다.
  **데이터시트가 아니라 멀티미터로 닫힌 첫 건입니다.**

## AI 도구 활용에 따른 성과

**커밋 118건 중 67건이 Claude 와의 공동 작업입니다.** 다만 이 숫자보다 중요한 것은
*무엇에 썼고 무엇에는 안 썼는가* 입니다.

### 원칙 — LLM 은 읽기만 하고, 판정은 코드가 한다

이것을 프로젝트 헌법 1번으로 두고 코드로 강제했습니다.

```
토폴로지가 질문을 던지고, 데이터시트가 답한다.
→ 결정적 코드가 플래그를 세운다 (LLM 없이)
→ LLM 은 그 플래그를 "지우기 위해서만" 호출된다
```

규칙 함수 `check(ctx)` 는 **순수 함수**입니다 — 네트워크·LLM·파일 IO·시간·난수 금지.
같은 입력에 다른 결과가 나오는 순간 검사 도구는 죽기 때문입니다.

### 성과 1 — LLM 이 읽고, **코드가 원문과 대조합니다**

데이터시트 PDF 에서 전기적 사실을 뽑을 때 LLM 을 씁니다. 그런데 거기서 끝내지 않습니다.

```
PDF 를 쪽별로 읽는다  →  LLM 이 값 + 인용문 + 쪽번호를 낸다
                      →  그 인용문이 그 쪽 원문에 정말 있는지 코드가 대조한다
                      →  없으면 버린다
```

**지어낸 출처가 DB 에 들어가는 것을 막을 수 있는 자리는 여기뿐입니다.**
저장기는 출처가 "있어" 보이면 받아들이기 때문입니다.

실제로 HLK-LD2410C 매뉴얼 5쪽을 돌려 사실 8건을 뽑았고 원문 대조 탈락 0건,
비용 약 $0.03 이었습니다.

### 성과 2 — AI 가 사람의 오류를 잡았습니다

사람이 손으로 `HLK-LD2410C` 의 "IO level 3.3V" 를 `voh_max` 로 적어 넣었습니다.
LLM 추출은 같은 자리에서 **`null` 을 돌려주며** 이렇게 적었습니다 —
*"IO 레벨 표기이지 Voh 규격값이 아니다."*

매뉴얼에 Voh 규격 표가 아예 없었습니다. **사람 쪽이 "모르면 모른다고 한다" 를
어긴 것이었습니다.** 항목을 `io_level` 로 나누고 근거 문구도 정확히 고쳤습니다.

<a id="llm-규칙-발견자"></a>

### 성과 3 — LLM 은 판정자가 아니라 **규칙 발견자**였습니다

같은 케이스를 LLM 에 그대로 던져 베이스라인을 쟀습니다. 같은 입력, 같은 채점자,
규칙 목록은 주되 **정답과 케이스 이름은 감췄습니다** (`r12-cross-domain` 이라는
이름 자체가 답이라서입니다).

| | 규칙 엔진 | LLM (Opus 5) |
|---|---|---|
| 합성 케이스 검출 | **15/15 (100%)** | 9/15 (60%) |
| 합성 케이스 오탐 | **0/13 (0%)** | 2/13 (15%) |
| **남의 실제 보드 6개 오탐** | **45건** | **0건** |

**합성에서 이긴 것은 우리가 낸 문제를 우리가 잘 푼 것이었습니다.**
실제 보드로 가니 결과가 뒤집혔습니다. 그리고 LLM 이 지적한 것 중 하나는
**진짜 결함**이었습니다 (위 「프로젝트 성과 3」의 `TFT_BL`).

우리가 내린 결론은 "LLM 이 나으니 LLM 을 쓰자" 가 아닙니다.

```
LLM 이 이상한 자리를 제안한다  →  사람·코드가 확인한다  →  패턴을 규칙으로 옮긴다
```

일단 규칙이 되면 **LLM 보다 낫습니다** — 같은 입력에 같은 답을 주고, 근거 위치를
양쪽에서 인용하고, PR 마다 자동으로 돕니다. LLM 은 셋 다 못 합니다.
데이터시트 추출이 이미 같은 모양(**LLM 이 읽고 코드가 대조한다**)이었습니다.

### 성과 4 — 오탐 45건의 뿌리가 하나였습니다

그 45건을 추적하니 원인이 하나로 모였습니다 —
**`Graph.pins_of()` 가 핀 *이름*이 아니라 *번호*를 돌려주고 있었습니다.**
그래서 `VIN`·`3V3` 같은 패턴이 하나도 안 걸렸습니다.
**핀맵 쪽에서 이미 한 번 고친 것과 똑같은 버그가 전원 도메인 추론 쪽에 남아 있었습니다.**

고친 뒤 **45 → 5**. 실제 보드에 돌려보지 않았으면 영원히 몰랐을 버그입니다.

### 팀 작업 방식 — 문서가 아니라 실행되는 규약

- **`CLAUDE.md` (프로젝트 헌법)** — 절대 원칙, 경쟁 경계, 범위 밖 목록, 알려진 버그.
  세션마다 먼저 읽습니다. **"이것과 충돌하는 제안은 하지 않는다"** 가 첫 줄입니다.
- **`.claude/skills/prefab-rule`** — 비전공 팀원이 자연어로 위험 상황을 설명하면
  규칙 코드 + 테스트 3종(양성/음성/미해결)으로 옮기는 절차를 고정했습니다.
- **`.claude/skills/prefab-datasheet`** — MPN → 데이터시트 → 사실 JSON 절차.

  때문이었습니다. 지금 CI 는 개수를 세지 않고 **계약 불변식**만 봅니다.
- **배포 검증 스크립트 자체가 검증을 안 하고 있었습니다.** `curl | python3 - <<EOF`
  에서 heredoc 이 stdin 을 차지해, 계약 검사 두 단계가 **한 번도 실제로 돈 적이
  없었습니다.** 배포하면서 발견해 고쳤습니다.

### 알려진 문제

**남은 것을 그대로 적습니다. 이 절이 비어 보이면 그게 더 의심스러운 문서입니다.**

- **남의 실제 보드에서 오탐 2건이 남아 있습니다.** 45 → 5 → **2** 로 줄였습니다.
  5 → 2 로 줄인 셋은 **규칙이 아니라 그 아래층 버그**였습니다 —
  `volts()` 가 `+3.3V` 를 3.0V 로, **`0.9V` 를 9.0V 로** 읽었고 ·
  전원 레일 판정이 핀 이름 대신 **번호**를 봤고 ·
  좌표가 없는 회로도 넷리스트에서 **좌표 클러스터링이 돌고** 있었습니다.

  남은 2건은 충전 IC(TP4056)의 `~CHRG`·`~STDBY` 가 `+3.3V` 로 풀업된 네트에서
  3.3V MCU 와 만나는 자리입니다. **오픈드레인이면 안전하고 푸시풀이면 위험한데
  넷리스트는 방향을 말해 주지 않습니다.** 팀이 이미 "풀업이 있다고 안전해지지 않는다"
  로 정해 뒀고 그 결정을 뒤집지 않았습니다 — 대신 제안 문구가 **데이터시트에서
  확인할 항목을 정확히 짚습니다.** 사실 하나만 넣으면 자동으로 해제됩니다.
- **R08 이 XTAL·UART 등 주변장치 전용 핀을 아직 안 봅니다.** USB 는 고쳤지만
  (칩 표의 `Chip.usb` + 커넥터 반대쪽 핀 이름) 크리스털이 달린 픽스처가 없어
  **일부러 미뤘습니다.** 확인할 보드 없이 표를 채우면 그게 다음 오탐입니다.
- **부품 사실이 3개뿐입니다.** 데이터시트 해제는 사실이 있어야 돕니다.
  없는 부품은 `UNRESOLVED` 로 나가고, **무엇이 있으면 풀리는지**를 같이 적습니다.
- **모듈 핀아웃 DB에 보드가 1개뿐입니다** (XIAO ESP32-C6).
  **이제 IPC-D-356 으로 들어온 보드에만 남은 문제입니다** — 회로도 넷리스트로 올리면
  핀 이름이 안 잘려서 좌표 복원 자체가 필요 없습니다.
- **`JQC-3FF-S-Z` 의 입력 하이 문턱(V_IH)을 모릅니다.** 그래서 R15 가 우리 보드에서
  `UNRESOLVED` 로 뜹니다 — 실제로 보고된 증상("LED가 ON은 되는데 OFF가 안된다")과
  **같은 네트**입니다. 모듈 보드에 모델명이 인쇄돼 있지 않아 회로도를 못 찾았고,
  측정 아니면 답이 안 나옵니다. **원인이라고 단정하지 않습니다** — 확인되면
  확정되거나 해제됩니다.

**닫힌 것** — 어떻게 닫혔는지가 남길 가치가 있는 것만 적습니다.

- ~~**새 회로도를 못 받았다**~~ → **보드가 되돌아왔습니다 (8/21).** 카메라(OV3660)가
  "안 먹어서" mmWave 로 복귀했고 **회로는 그대로, 코드만 바뀌었습니다.**
  새 펌웨어는 `v2.firmware/` 픽스처로 고정했습니다. 칩 표의 `ESP32-S3` 는 그대로
  둡니다 — 출처를 달아 넣은 값이라 지울 이유가 없고, 보드가 또 바뀌면 바로 씁니다.
- ~~**R12 근거 문구가 풀다운을 "풀업" 이라고 적는다**~~ → 저항의 **반대쪽 터미널**을
  보고 가릅니다. 같은 종류로 하나 더 닫았습니다 — 설계 원칙 4번이 `K1와` 를
  하지 말라는 **예시로 들고 있는데 화면에 그대로 나가고 있었습니다.**

- ~~`R11`·`R12` 중복 검출~~ → **근거 기준으로 합칩니다.**
  심각도로 고르게 만들었더니 차별 등급 R08 이 기본 등급 R12 에 먹혀 사라졌습니다.
  **기준은 심각도가 아니라 "새로운 근거를 내놓는가" 입니다.**
- ~~KiCad 보드에서 미연결 패드를 못 알아봄~~ → `unconnected-(U3-SPICLK-Pad22)` 가
  네트명 14자 절단으로 `-SPICLK-PAD22)` 가 되어 배선처럼 보였습니다. 패드 수로 판단합니다.
- ~~**`_IN_ACTIVE_LOW` 의 R12**~~ → **측정으로 닫혔습니다.** 아래 「하드웨어가 규칙을
  기각한 두 번」 참고.
- ~~**`_IN_ACTIVE_LOW`의 R12**~~ — **닫혔습니다 (8/19).** 하드웨어 담당이 릴레이 모듈을
  보드에서 뽑아 `IN`↔`VCC` 를 20kΩ·2MΩ 범위로 측정했고 둘 다 `OL` 이었습니다.
  저항성 5V 풀업이 없으므로 그 핀을 통해 5V 가 올라올 경로가 없습니다 — **오탐이었습니다.**
  `parts/jqc-3ff-s-z.json` 에 실측값으로 기록했고 자동으로 해제됩니다.
  **데이터시트가 아니라 측정으로 풀린 첫 건입니다.**

## 해커톤 참여 후기

12일 동안 가장 크게 배운 것 넷을 적습니다. **잘된 이야기보다 틀렸던 이야기가
길어졌는데, 실제로 그쪽에서 더 많이 배웠기 때문입니다.**

### 하나 — "검증 데이터를 모으면 된다" 가 틀렸습니다

계획에 *"오픈소스 저장소 30~50개로 재현율을 측정한다"* 라고 적었습니다.
스크립트를 짜서 커밋 **5,299건**을 훑었고, 핀이 바뀐 커밋은 **2건** 나왔습니다.

처음에는 스크립트를 의심했습니다. 팀에서 나온 지적이 방향을 바꿨습니다 —
**"우리가 긁어온 게 완성품이라서 그런 것 아니냐."**

맞았습니다. **공개 저장소에는 작동하는 보드만 올라옵니다.** 우리가 찾는 결함은
올리기 전에 고쳐져서 커밋 사이에 안 남습니다. 데이터가 부족한 게 아니라
**그런 데이터가 존재하지 않는 자리를 판 것**이었습니다.

그래서 이걸 실패로 지우지 않고 **음성 결과로 기록했습니다.**
못 한 일을 숨기지 않는 것이 이 프로젝트의 원칙이기도 하고,
같은 함정을 다음 사람이 또 팔 이유가 없기 때문입니다.

### 둘 — 0건이 나왔을 때, 규칙이 아니라 입력을 의심해야 했습니다

실제 오픈소스 보드 3개에 차별 규칙을 돌렸더니 **발견 0건**이었습니다.
"보드가 멀쩡해서" 라고 넘어갈 뻔했습니다.

통제 실험을 했습니다. **우리 보드에서 핀 이름만 번호로 바꿨더니** 핀맵이 11 → 0,
발견이 5 → 2건이 됐습니다. 원인은 규칙이 아니라 **입력 형식**이었습니다.
IPC-D-356 은 제조용 파일이라 사람이 읽는 이름을 안 싣습니다. 우리 보드가 되던 것은
쓰던 도구가 실크 이름을 실어 줬기 때문이고, **한 도구에서만 되는 걸 모르고 있었습니다.**

같은 회로도를 다른 형식으로 뽑으면 이렇습니다.

| 같은 보드에서 얻는 것 | IPC-D-356 | kicadxml |
|---|---|---|
| 부품번호 | 0% | **100%** (52/52) |
| 데이터시트 URL | 0% | **100%** |
| 핀 이름 | **0%** | **62%** (115/183) |

파서를 하나 더 만들어 벽을 뚫었습니다. **계획에 없던 작업이었고, 하길 잘했습니다.**

### 셋 — 잘 나온 숫자를 의심해야 했습니다

선배에게 자문을 받으며 들은 말이 있습니다 —
*"다 해놨는데, 그게 실제 적용했을 때 예상과 다를 수 있다."*

그때 우리 오탐율은 0% 였습니다. 남의 실제 보드 6개에 돌리니 **오탐 45건**이 나왔습니다.
**합성 케이스에서의 0% 는 우리가 낸 문제를 우리가 잘 푼 것**이었습니다.

같은 자리에서 LLM 베이스라인도 처음 쟀는데, 실제 보드에서는 **LLM 이 우리를 이겼습니다**
(오탐 0건, 게다가 진짜 결함 1건 지적). 발표에서 *"그냥 GPT 한테 주면 되는 거 아닌가요"*
라는 질문이 반드시 나올 텐데, 그 답에 댈 숫자가 그때까지 하나도 없었습니다.

져 본 것이 이 프로젝트에서 제일 값진 순간이었습니다. 오탐 45건의 뿌리를 찾아
**45 → 5** 로 줄였고, LLM 이 지적한 결함에서 **R14** 가 나왔습니다.

### 넷 — 전공이 다른 사람이 있어야 안 만들 것을 안 만듭니다

소프트웨어만 있는 팀이었으면 **R13** 을 만들었을 것입니다. 하드웨어 담당이
"문제 안 됨" 이라고 판정해서 **구현 전에 기각**됐습니다.
`_IN_ACTIVE_LOW` 경고는 릴레이 모듈을 보드에서 뽑아 멀티미터로 재서 닫았습니다.

**검사 도구에서는 안 만든 규칙도 성과입니다.** 오탐률이 높은 린터는 3일이면 꺼지고,
꺼진 린터는 없는 린터와 같기 때문입니다.

### 남은 것

12일로는 **부품 사실 3개**, **실측 검증 케이스 2개**까지가 한계였습니다.
남의 보드 오탐도 **2건** 남아 있습니다 (45 → 5 → 2). 다만 이제 그것들이
*무엇인지* 와 *왜 남았는지* 는 문서에 적혀 있고, 남은 2건은 데이터시트 사실
하나면 풀립니다.

그리고 마지막 날에 **우리 보드가 실제로 고장 났고, 그 자리를 우리 도구가 짚었습니다.**
12일 중 제일 값진 순간이 마지막에 왔습니다.

> 정리한 것입니다.

## IPC-D-356 파싱 노트

같은 형식을 다룰 사람을 위해 남깁니다.
고정폭 레코드이며 오프셋은 다음과 같습니다 (0-indexed, 실측 확인).

```
[0:3]   레코드 타입   317=through-hole/via, 327=SMT
[3:17]  네트명
[20:26] reference designator
[26]    '-' 구분자
[27:31] 핀 이름        ← 4자에서 잘림
[32:37] 드릴
[41:49] X 좌표 (0.0001 inch)
[49:57] Y 좌표
```

주의할 점 세 가지.

- **핀 이름이 4자로 절단됩니다.** `LP-GPIO0` → `LP-G`. 정확한 GPIO 번호는
  모듈 핀아웃 DB 없이는 알 수 없습니다.
- **MPN·부품값·제조사가 없습니다.** 데이터시트 기반 판정을 하려면 BOM이 반드시 필요합니다.
- **여러 패드의 이름이 전부 같게 나오는 부품이 있습니다.** 릴레이 모듈의 6개 패드가
  모두 `pad-`로 나왔습니다. X좌표 클러스터링으로 제어부와 스위치부를 분리했습니다.

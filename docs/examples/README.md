# 응답 예시

**여기 있는 JSON은 실제 검사 결과가 아닙니다.** 계약이 어떤 모양이어야 하는지 적은 목표 명세입니다.

리포에서 "실제 검사 결과"는 [`apps/web/src/mocks/check.json`](../../apps/web/src/mocks/check.json)
하나뿐입니다. 그건 실제 보드를 파서·규칙 엔진에 돌려 얻은 값이고 손으로 적은 숫자가 없습니다.
이 폴더의 파일은 그 반대입니다 — **손으로 적었고, 아직 일어나지 않은 일입니다.**
숫자를 발표나 문서에 인용하지 마세요.

---

## `check.target-with-firmware.json`

R7 · R8 이 구현된 뒤 `GET /api/v1/checks/{id}` 가 **이렇게 응답하면 된다**는 예시입니다.

| | |
|---|---|
| 입력 | 실제 넷리스트 + 팀원 초판 펌웨어 (둘 다 리포에 있는 실제 파일) |
| 발견 | 6건 — R7×2 · R8 · R12×2 · R11 |
| 근거 | [`apps/api/tests/fixtures/esp32-c6-presence-smart-light.EXPECTED.md`](../../apps/api/tests/fixtures/esp32-c6-presence-smart-light.EXPECTED.md) |

**용도 둘.**

1. **백엔드**: 규칙을 구현할 때 목표로 삼을 응답 모양. 필드 이름·중첩·`null` 위치를 그대로 맞추면 프론트 수정이 필요 없습니다.
2. **프론트**: 발견이 3건에서 6건으로 늘고 펌웨어 근거가 붙었을 때 리포트가 깨지지 않는지 미리 확인했습니다.

이 예시로 화면을 돌려보고 실제로 두 가지를 고쳤습니다.

- 발견이 심각도 순으로 정렬되지 않고 있었습니다 (서버 순서 그대로 렌더)
- **펌웨어를 읽었는데도 카드가 "펌웨어를 올리면 채워집니다"라고 말했습니다.**
  소스를 받았는지와 그 판정에 근거로 쓰였는지를 구분하지 않았기 때문입니다.

### 로컬에서 이 예시로 화면 띄우기

계약대로 응답하는 아무 서버에 이 파일을 그대로 얹으면 됩니다.

```bash
VITE_API_BASE=http://127.0.0.1:8000 pnpm --dir apps/web dev
# → http://localhost:5173/r/chk_target01
```

### 확정되지 않은 부분

- ~~R13~~ 은 **기각됐습니다.** 하드웨어 담당 판정이 "문제 안 됨"이라 예시에서 제거했습니다.
- **핀 이름** (`U1.D5` 등) 은 좌표로 추론해 확정한 값입니다. 실물 실크 대조 전입니다.
  자세한 근거는 [`docs/CHIPS.md`](../CHIPS.md) 모듈 핀아웃 절에 있습니다.
- `evidence[].kind === "netlist"` 의 `text` 안에서 핀을 `U1.D5 (GPIO23, 패드명 SDIO)` 처럼
  적었습니다. 이건 예시일 뿐이고, 실제로는 구조화 필드로 받는 쪽이 낫습니다
  ([`_docs/백엔드_요청서.md`](../../_docs/백엔드_요청서.md) 2-3 절).

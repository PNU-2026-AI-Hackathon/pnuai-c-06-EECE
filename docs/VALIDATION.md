# 검증 방법론

우리가 잡는다고 주장하는 것을 **정말 잡는지**, 잡지 말아야 할 것을 **안 잡는지** 재는 방법.

로드맵 8/25–26 항목이지만, 백엔드가 파서를 만들 때 커밋 쌍을 뽑을 수 있게
설계해 두어야 하므로 미리 정합니다.

---

## 넘지 않는 선

**근거와 검증은 다른 것입니다.**

| | 무엇을 쓰나 | 어디에 나오나 |
|---|---|---|
| **근거** (evidence) | 넷리스트 · 펌웨어 소스 · 데이터시트 | 사용자에게 보이는 발견 카드 |
| **검증** (validation) | 오픈소스 저장소의 수정 커밋 | 우리 테스트 · 발표 자료 |

> **다른 저장소의 커밋은 근거가 아닙니다.**
> "GPIO34는 입력 전용"의 근거는 Espressif 데이터시트이지, 남이 그렇게 고쳤다는 사실이 아닙니다.
> 하드웨어 담당이 자기 보드 앞에서 확인할 수 있는 것만 `evidence[]`에 넣습니다.

이 선을 넘으면 "결국 통계 아니냐"는 질문에 답할 수 없게 됩니다.
설계 원칙 1번(판정은 결정적 코드가 한다)이 무너집니다.

**예외 하나** — R10(드리프트)은 "회로도 변경 후 코드 미추종"이 규칙 정의 자체라
git 이력이 검증 데이터가 아니라 **입력**입니다. 이 경우 커밋 정보가 근거에 들어갑니다.

---

## 왜 수정 커밋이 정답지인가

사람이 "이건 버그다"라고 판단해서 고친 기록입니다. **우리가 심은 것이 아닙니다.**

```
수정 직전 커밋  →  도구 실행  →  잡아야 한다   (놓치면 미검출)
수정 커밋       →  도구 실행  →  잡으면 안 된다 (잡으면 오탐)
```

한 쌍에서 두 가지를 동시에 잽니다. 픽스처 12/12 통과보다 이쪽이 훨씬 강한 주장입니다.

---

## 규칙별 난이도

수집 난이도가 규칙마다 크게 다릅니다. 쉬운 것부터 합니다.

| 규칙 | 필요한 입력 | 수집 | 비고 |
|---|---|---|---|
| **R1** 쓸 수 없는 핀 사용 | 펌웨어 + 칩 표 | ✅ 쉬움 | ESP32 펌웨어 저장소는 매우 많음 |
| **R5** 지원하지 않는 조합 | 펌웨어 + 칩 표 | ✅ 쉬움 | 위와 동일 |
| **R7** 코드가 쓰는 핀 미연결 | 펌웨어 **+ 넷리스트** | ⚠ 어려움 | 회로도까지 공개하는 저장소가 드묾 |
| **R8** 연결됐는데 초기화 안 함 | 펌웨어 **+ 넷리스트** | ⚠ 어려움 | 위와 동일 |
| **R10** 드리프트 | 펌웨어 + 넷리스트 + git | ⚠ 어려움 | 회로도 파일이 버전 관리되는 저장소 필요 |
| **R11 · R12** 전원 도메인 | 넷리스트 | ⚠ 어려움 | 오픈 하드웨어 저장소 필요 |

**R1·R5는 펌웨어만 있으면 됩니다.** 목표 30~50개를 채울 수 있는 건 사실상 이 둘입니다.
회로도가 필요한 규칙은 오픈 하드웨어 저장소로 범위가 좁아지므로 표본이 작다고 정직하게 밝힙니다.

---

## 수집 절차

### 1. 후보 저장소

- ESP32 계열 펌웨어를 담은 공개 저장소
- 라이선스 확인 (검증 목적 사용이라 대부분 문제없지만 기록은 남긴다)
- 회로도가 필요한 규칙은 KiCad·Flux 파일이 함께 있는 오픈 하드웨어 저장소로 한정

### 2. 수정 커밋 찾기

커밋 메시지로 1차 필터한 뒤 **사람이 확인**합니다. 자동 필터만 믿지 않습니다.

```
fix pin / wrong gpio / gpio typo / pinout / input only /
strapping / adc2 / wifi adc / swap pin / correct pin
```

diff가 핀 번호 상수 하나만 바꾼 커밋이 가장 깨끗한 표본입니다.

### 3. 라벨링

한 쌍마다 아래를 기록합니다. 담당은 권지효(검증 데이터셋 라벨링).

```jsonc
{
  "repo": "owner/name",
  "rule": "R1",
  "buggy_commit": "abc1234",
  "fixed_commit": "def5678",
  "chip": "esp32",
  "expected": "detect",          // buggy 에서 잡혀야 한다
  "note": "GPIO34 를 OUTPUT 으로 설정. 수정에서 GPIO25 로 변경",
  "labeled_by": "권지효"
}
```

### 4. 실행과 측정

```
재현율 = 잡은 buggy 쌍 / 전체 buggy 쌍
오탐율 = 잡힌 fixed 쌍 / 전체 fixed 쌍
```

## 편향을 정직하게 적는다

이 방식에는 구조적 한계가 있습니다. 발표에서 **먼저** 말합니다.

1. **커밋 메시지로 찾았으니 메시지를 잘 쓴 프로젝트만 모입니다.** 조용히 고친 버그는 표본에 없습니다.
2. **수정된 버그만 모입니다.** 아직 아무도 못 찾은 버그에 대해서는 아무 말도 못 합니다.
3. **표본이 작습니다.** 30~50개는 통계적 주장을 하기엔 적습니다. "이 표본에서는" 이라고 한정합니다.
4. **오탐율의 분모가 좁습니다.** fixed 커밋만 보므로, 애초에 정상인 수많은 코드에서의 오탐은 못 잽니다.

4번을 보완하려면 **버그와 무관한 정상 저장소**를 별도로 돌려 오탐만 따로 재야 합니다.
이쪽 표본이 오히려 더 중요합니다 — 오탐이 많은 도구는 아무도 안 씁니다.

## 산출물

```
apps/api/tests/validation/
├─ dataset.jsonl        라벨링한 커밋 쌍
├─ run_validation.py    전체 실행 → 재현율·오탐율
└─ results/             실행 기록 (날짜별)
```

측정 결과는 **좋든 나쁘든 그대로** README 현재 상태에 적습니다.
숫자가 나쁘면 숫자를 고치는 게 아니라 규칙을 고칩니다.

## 골든 테스트와의 관계

| | 무엇을 막나 | 언제 도나 |
|---|---|---|
| 규칙당 픽스처 3개 (양성/음성/미해결) | 규칙 자체가 깨지는 것 | 매 커밋 |
| 실제 보드 골든 테스트 | 실보드 결과가 조용히 바뀌는 것 | 매 커밋 |
| **검증 데이터셋** | **현실에서 안 통하는 것** | 주기적 · 발표 전 |

앞의 둘은 우리가 만든 입력이라 "실제로 통하는가"에는 답하지 못합니다.
세 번째만 그 질문에 답합니다.

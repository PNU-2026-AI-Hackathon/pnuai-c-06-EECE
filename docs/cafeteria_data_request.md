# 금정회관 학생식당 협의 — 데이터 요청 정리

> 식당 관계자(생협/영양사) 미팅용. 앱·DB 구조 기준으로 "무엇을, 얼마나 자주, 어떤 형태로"
> 받아야 하는지 정리. 팀: PNU 밥묵자 (제7회 PNU 창의융합AI해커톤)

## 0. 핵심 메시지 (협의 첫마디)

- 별도 장비·센서 설치 없음. **앱 식권 판매 데이터 자체가 대기열 데이터**가 되는 구조.
- 식당 측 부담은 ① 기초 정보 1회 제공 ② 식단 등록(또는 기존 공개 식단 활용 동의)
  ③ 배식대에서 QR 확인 — 이 3가지가 전부.

## 1. 한 번만 받으면 되는 것 (정적 데이터)

| 항목 | 예시 | DB 저장 위치 |
| :-- | :-- | :-- |
| 배식 라인 구성 | 1층 정식 / 1층 단품 / 2층 정식 | `dining_lines` |
| 라인별 가격 | 정식 4,000원 등 | `menus.price` |
| 운영 시간 | 평일 11:00~14:00 등 (라인별로 다르면 각각) | `restaurants.operating_hours` |
| **1인당 평균 배식 시간** | 라인별 약 20~30초 (관계자 체감치면 충분) | `dining_lines.avg_service_sec` |
| 시간대별 피크 패턴 | 12:00~12:30 최대 혼잡 등 (체감치) | AI 예측 보정용 |
| 하루 평균 식수 인원 | 라인별 대략치 | 혼잡도 임계값 보정용 |

※ 예상 대기시간 정확도는 `avg_service_sec`에 달려 있음 — 이것만은 꼭 물어볼 것.

## 2. 매일 받아야 하는 것 (식단)

**옵션 A (권장): 기존 공개 식단 활용 동의만 받기**
부산대 홈페이지에 이미 식단이 공개됨 (대학생활 → 식단안내).
→ 우리가 자동 수집(스크래핑/API)해도 되는지 동의만 받으면 식당 측 추가 업무 0.

**옵션 B: 운영자 대시보드에서 직접 등록**
백엔드 운영자 대시보드의 메뉴 관리 기능으로 영양사가 매일 아침 등록.
→ 식당 측 업무 발생. 협의에서 A 거부 시의 대안.

| 항목 | 주기 | DB |
| :-- | :-- | :-- |
| 라인별 오늘 메뉴 (메인+반찬) | 매일 | `menus` (menu_date) |
| 품절/조기 마감 | 발생 시 | `dining_lines` 상태 (운영자 대시보드) |
| 휴무/방학 단축 운영 | 수시 | `restaurants.operating_hours` |

## 3. 운영 협조 (데이터가 아니라 "행동")

1. **배식대 QR 확인** — 배식 직원이 태블릿/폰으로 학생 QR 스캔 (운영자 대시보드 제공).
   스캔 = 식권 검증 + 대기열에서 제거 → 실시간 대기 인원의 정확도가 여기서 나옴.
2. **호출 운영 방식 합의** — 앱이 "내 차례" 알림을 보내는 기준(앞 N명 이하)을
   식당 배식 속도에 맞춰 정할 것.
3. **결제/정산 방식** — MVP는 Mock 결제. 실결제 도입 시 생협 정산 체계와 연동 필요
   (수수료·정산 주기 — 해커톤 범위 밖이지만 의향만 확인).

## 4. 협의에서 확인할 질문 리스트

- [ ] 라인 구성과 가격이 우리가 아는 것(1층 정식·1층 단품·2층 정식, 4,000원)과 맞는지
- [ ] 1인당 평균 배식 시간은 체감상 몇 초인지 (라인별)
- [ ] 공개 식단 데이터를 앱에서 사용해도 되는지 (옵션 A 동의)
- [ ] 배식대에서 QR 스캔이 운영상 가능한지 (인력·동선)
- [ ] 피크 시간대와 하루 평균 식수 인원
- [ ] 시범 운영(파일럿) 기간·범위에 대한 의향 — 예: 1개 라인, 점심시간만
- [ ] 담당 연락 창구 (메뉴 변경·운영 이슈 발생 시)

## 5. 받은 데이터가 흘러가는 곳 (팀 내부 참고)

```
정적 정보  → 백엔드가 restaurants/dining_lines/menus 테이블에 시드
식단(매일) → 옵션A: 수집 스크립트 → menus / 옵션B: 운영자 대시보드 입력
QR 스캔    → POST /api/tickets/verify → tickets.status='used' → 대기열 자동 감소
```

앱(프론트)은 수정 불필요 — 이미 Supabase 모드에서 이 테이블들을 읽도록 되어 있음.
협의 결과는 `backend_handoff.md`에 반영해서 백엔드와 공유할 것.

## 2. 바로 되살릴 수 있는 것 — F-4 (한 줄입니다)

`routes/Upload.tsx` 에 이렇게 적어두셨습니다:

```tsx
// 샘플은 목이 아는 검사다. 서버가 붙으면 서버는 이 id 를 모르므로 404 가 난다.
// 서버가 샘플 검사를 직접 만들어 주면 그때 되살린다 (백엔드_요청서 F-4).
{usingMock && ( ... "샘플 보드로 실행" ... )}
```

**서버가 이제 그 id 를 압니다.** 켜질 때 실측 보드 결과 하나를 저장소에 넣어 둡니다.

```
GET /api/v1/checks/chk_sample01     →  치명 4 · 경고 1 · R07·R08 포함
```

`sampleCheck.check_id` 와 **같은 값**(`chk_sample01`)이라, 목 모드와 서버 모드에서
같은 버튼이 같은 화면으로 갑니다. `usingMock &&` 게이트만 떼면 됩니다.

### 다만 하드코딩은 하지 말아 주세요

서버가 샘플을 못 실었으면 그 id 가 없습니다 (배포 이미지에 JSON 이 안 실린 경우).
그때 404 가 나면 게이트를 뗀 것이 오히려 손해입니다. **루트가 알려줍니다:**

```bash
curl https://<api>/
{ "service": "prefab-api", "docs": "/docs",
  "contract": "/api/v1/rules",
  "sample_check": "/api/v1/checks/chk_sample01" }   ← 없으면 이 키가 아예 없습니다
```

`sample_check` 가 있을 때만 버튼을 띄우면 안전합니다.
(이 엔드포인트는 계약에 없는 안내용 응답이라 필드를 추가해도 계약 위반이 아닙니다.)

**새 엔드포인트가 아닙니다.** 기존 `GET /api/v1/checks/{id}` 로 그대로 나옵니다.

## 3. 확인만 해주세요 — 응답에 실제로 담기기 시작한 것

전부 **계약에 이미 있던 값**인데, 지금까지 실제로 안 나오던 것들입니다.
코드를 보니 세 개 다 이미 처리하고 계신 것 같은데, 실물로 한 번 봐 주세요.

### 3-1. `net: null` 인 발견

R07(코드가 쓰는 핀이 회로도에 미연결)은 **네트가 없는 발견**입니다. 핀은 있는데
아무 네트에도 안 붙어 있는 게 판정의 내용이라서요. 샘플에 2건 들어 있습니다.

`FindingCard.tsx` 의 `{finding.net && ...}` 가 이미 맞게 처리합니다. 화면에서
네트 자리가 비었을 때 레이아웃이 어색하지 않은지만 봐 주세요.

### 3-2. `verdict: "UNRESOLVED"`

R11 이 **판정을 미루는 경우**가 생겼습니다 (아래 4번). `VerdictBadge` 의
"판정 보류" 가 그대로 쓰입니다. 실측 보드에서는 안 나오고, 네트명이 잘린 보드에서만
나옵니다.

### 3-3. 파이프라인 1단계 `detail` 이 길어질 수 있습니다

```
네트 8 · 부품 10 · ⚠ 네트명 2개가 14자에 꽉 참 (_IN_ACTIVE_LOW · D_POS_SWITCHED)
— 원래 이름이 잘렸을 수 있습니다
```

`Pipeline.tsx` 가 `<p>` 로 그리고 있어서 줄바꿈은 될 텐데, 좁은 화면에서 어떻게
보이는지만 확인 부탁드립니다. **말줄임(`truncate`)은 걸지 말아 주세요** — 이 문장이
"왜 어떤 규칙이 조용한지"를 설명하는 유일한 자리입니다.

---

## 4. 왜 R11 이 판정을 미루나 (A++2)

넷리스트의 **네트명 칸은 14자**입니다. 핀 이름이 4자에서 잘리는 것과 같은 문제인데
더 조용하게 아픕니다.

작업하다 실측 보드에서 증거를 찾았습니다:

```
_IN_ACTIVE_LOW   ← 14자, 앞이 잘린 흔적(_로 시작)
D_POS_SWITCHED   ← 14자, 같은 패턴
```

원래 이름은 `RELAY_IN_ACTIVE_LOW` · `LED_POS_SWITCHED` 였을 겁니다.
**이 도구는 뒤가 아니라 앞을 잘랐습니다.**

그래서 `SENSOR_OUT_3V3` 같은 이름을 만나면 `..._3V3` 이 `_3V3` 인지 `_3V35` 의
앞부분인지 알 수 없습니다. 3.3V 를 3V 로 읽고 0.3V 차이로 경고를 내면 그게 오탐이라,
그 경우엔 `UNRESOLVED` 로 두고 "EDA 원본에서 전체 이름을 확인해 주세요" 라고 적습니다.

**화면이 할 일은 없습니다.** 왜 그런 문구가 나오는지만 알아두시면 됩니다.

## 6. 결정이 필요한 것 — R10 (혼자 못 정합니다)

남은 규칙 하나가 R10(회로도 변경 후 코드 미추종)인데, **git 이력을 계약의
네 번째 입력으로** 받아야 합니다. 그러면 계약이 바뀌고 프론트 타입도 바뀝니다.

순서는 요청서 3-5 에 적어두신 대로 **계약 → 프론트 타입 → 카탈로그** 입니다.
합의 전에는 손대지 않겠습니다.

### 그동안 R10 없이 드리프트를 보여주는 길은 만들어 뒀습니다 (F-1)

`.github/workflows/drift.yml` 이 PR 마다 **같은 엔진을 base 입력과 head 입력에**
각각 돌려 발견 목록을 비교하고 코멘트를 답니다. 새 치명 발견이 생기면 빨간불입니다.

실측 보드에서 센서 배선만 D2 → D4 로 옮기고 코드를 그대로 뒀을 때 (넷리스트 **두 줄** 차이):

```
🔴 새로 생긴 발견
  R07 · U1.D2   코드가 D2(GPIO2) 핀을 출력으로 구동합니다.
                그런데 회로도에서 이 핀은 아무 네트에도 연결돼 있지 않습니다.
  R08 · D4      회로도는 D4(GPIO22)를 PRESENCE_3V3 로 배선해 뒀는데,
                코드에는 이 핀이 한 번도 나오지 않습니다.
```

발표에서 이 화면을 쓰실 거면 말씀해 주세요. 코멘트 마크다운을 그대로 슬라이드에
붙일 수 있게 문구를 다듬겠습니다.

## 7. 배포 후 확인

```bash
./apps/api/scripts/smoke.sh https://<배포-URL>
```

6단계가 **샘플 검사까지** 확인합니다. 여기서 `sample_check 가 없다` 가 뜨면
배포 이미지에 샘플 JSON 이 안 실린 것이니, 버튼을 붙이기 전에 알려주세요.

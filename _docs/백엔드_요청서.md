## 0. 로컬에서 프론트-백엔드를 붙일 때 필요한 것

### 0-1. 로컬 실행 방법 한 줄

`uvicorn web.app:app --reload --port 8000`이면 되는지, 다른 준비(환경변수 · API 키)가
있는지만 알려주세요. 붙일 때는 `VITE_API_BASE=http://localhost:8000`을 씁니다.

배포 URL은 **나중에** 주셔도 됩니다. 그때 환경변수만 갈아끼우면 됩니다.

### 0-2. CORS — 지금 넣어주세요

```
허용 origin: http://localhost:5173, <배포 URL — 정해지면 추가>
허용 method: GET, POST, OPTIONS
```

`POST /api/v1/checks`는 `multipart/form-data`라 **프리플라이트(OPTIONS)가 먼저 날아갑니다.**
GET만 열어두면 로컬에서 붙일 때부터 업로드가 통째로 막힙니다.
배포는 미루더라도 이건 지금 넣는 게 쌉니다.

### 0-3. `status: "running"`일 때 `pipeline`을 채워주세요

진행 화면(`/c/{id}`)은 **1초마다 `GET /api/v1/checks/{id}`를 폴링해서 `pipeline` 배열만 그립니다.**

- `status: "running"`이면 → 지금까지 끝난 단계가 실려 있어야 합니다. 나머지는 아직 안 실려도 됩니다.
- `status: "done"`이면 → 프론트가 자동으로 `/r/{id}`로 넘어갑니다.

running인데 `pipeline`이 빈 배열이면 진행 화면이 빈 화면이 됩니다.
검사가 1초 만에 끝난다면 이 항목은 무시하셔도 됩니다 — **그 경우 그렇다고만 알려주세요.**
바로 리포트로 보내도록 화면을 바꾸겠습니다.

### 0-4. 오류 응답 형식 고정

프론트는 `error.message`를 **사용자에게 그대로 보여줍니다.** 따로 문구를 만들지 않습니다.

```json
{ "error": { "code": "NETLIST_REQUIRED", "message": "넷리스트 파일이 필요합니다." } }
```

계약에 있는 4개(`NETLIST_REQUIRED` · `NETLIST_PARSE_FAILED` · `FILE_TOO_LARGE` · `CHECK_NOT_FOUND`)
외에 새 코드가 생기면 알려주세요. 코드를 몰라도 메시지는 뜨지만, 화면에서 다르게 다뤄야 할 게 있을 수 있습니다.

## 1. 지금 화면이 "지어내고 있는" 값 — 계약으로 대체하고 싶습니다

### 1-1. `GET /api/v1/rules` 언제 됩니까 — **프론트는 준비 끝났습니다**

원래 업로드 화면에 `"코드 대조 규칙 5개 실행 불가"`처럼 숫자가 박혀 있었습니다.
규칙이 늘면 즉시 거짓말이 되는 값이라 **지웠습니다.**

지금은 이렇게 동작합니다.

| 카탈로그 | 화면 |
|---|---|
| 있음 | `needs`를 세어서 `실행 못 하는 규칙 2개 — R11 · R12` / `아직 구현 전 5개 — R1 · R5 · R7 · R8 · R10` |
| 없음 | **개수를 말하지 않습니다.** 지어내지 않기 위해서입니다 |

계약대로 응답하는 임시 서버로 양쪽 경로를 확인해 뒀습니다.
**엔드포인트가 뜨는 순간 프론트 수정 없이 숫자가 붙습니다.**

- `implemented: false`인 규칙도 꼭 포함해 주세요. "아직 구현 전"으로 따로 표시합니다.
- 목 모드용 `rules.json`은 **안 주셔도 됩니다.** 없으면 개수를 안 쓰는 쪽으로 처리했습니다.

### 1-2. `summary`에 전체 규칙 수가 없습니다

리포트 요약 타일에 "실행한 규칙 2/12"를 표시하는데, 지금은 이렇게 계산합니다.

```ts
`${summary.rules_run}/${summary.rules_run + summary.rules_skipped}`
```

**이 합이 항상 규칙 카탈로그 전체 개수와 같습니까?**
"해당 없어서 애초에 후보에도 안 든 규칙"이 생기면 이 합이 전체보다 작아집니다.
그렇다면 `summary.rules_total`을 추가해 주세요. 같다면 지금 방식 그대로 두겠습니다.

### 1-3. `created_at` 시간대

리포트 헤더에 `created_at.slice(0, 10)`으로 **날짜만** 찍고 있습니다.
계약 예시가 `Z`(UTC)라서 그대로 두면 한국 시간 오전 9시 이전 검사는 하루 전 날짜로 보입니다.

- UTC로 유지 → 프론트에서 KST로 변환해 표시하겠습니다. **이쪽을 권합니다.**
- KST 문자열로 준다 → 그대로 찍겠습니다.

둘 중 뭔지만 알려주세요.

## 2. 계약 확장 제안 — 급하지 않습니다 (8/25 이후여도 됨)

### 2-1. `netlist` 근거에 구조화된 연결 정보

발견 카드의 "회로도가 아는 것" 레인에 **핀-네트 연결을 도식으로 그리려고 합니다.**
지금은 `evidence.text`가 줄바꿈으로 이어진 문자열이라, 그리려면 프론트가 이 문자열을
다시 파싱해야 합니다. 그건 파서를 두 벌 만드는 것이고 계약 위반입니다. 그래서 **안 했습니다.**

제안 (기존 `text`는 그대로 두고 선택 필드로 추가):

```json
{
  "kind": "netlist",
  "text": "U2.OUT → PRESENCE_3V3\nU1.LP-G → PRESENCE_3V3",
  "nodes": [
    { "ref": "U2", "pin": "OUT",  "net": "PRESENCE_3V3", "role": "source" },
    { "ref": "U1", "pin": "LP-G", "net": "PRESENCE_3V3", "role": "sink" }
  ],
  "highlight": ["U2.OUT"]
}
```

- `role`은 `source` / `sink` / `passive` 정도면 충분합니다. 판정에 못 쓰겠으면 빼도 됩니다.
- `nodes`가 없으면 지금처럼 `text`를 그대로 보여줍니다. **없다고 화면이 깨지지 않습니다.**
- **지금 당장은 필요 없습니다.** R7·R8이 돌기 시작해서 코드-회로도 대조가 실제로 나올 때
  같이 넣는 게 맞다고 봅니다.

### 2-3. 넷리스트 핀에 실크 라벨·GPIO를 실어주세요 — **R7·R8의 선행 조건**

이걸 못 하면 R7·R8이 우리 보드에서 못 돕니다. 우선순위 2번에 뒀지만
**R7·R8을 만들기 시작하는 시점에는 이게 먼저 끝나 있어야 합니다.**

픽스처를 파다 확인한 사실입니다.

```
U1 레코드 25개 → 이름 종류 18개
LP-G × 3   (LP_GPIO0 / LP_GPIO1 / LP_GPIO2)
SDIO × 3   (SDIO_DATA1 / DATA2 / DATA3)
```

IPC-D-356이 핀 이름을 4자에서 자르기 때문에 **물리적으로 다른 핀이 같은 이름으로 뭉칩니다.**
그래서 지금 응답으로는 `_IN_ACTIVE_LOW`에 붙은 `U1.SDIO`가 D3인지 D4인지 D5인지 알 수 없습니다.

```jsonc
// 현재
{ "ref": "U1", "pin": "SDIO" }

// 필요
{ "ref": "U1", "pin": "SDIO", "silk": "D5", "gpio": 23 }
```

`parts[].pins`도 같은 문제입니다 — 25개 패드가 18개로 뭉쳐서 D3·D4·D5가 `SDIO` 하나로 보입니다.

**좌표로 풀립니다.** 헤더가 두 열이고 피치가 0.1 inch라서 Y 내림차순이 실크 순서입니다.
대조표를 [`docs/CHIPS.md`](../docs/CHIPS.md) 모듈 핀아웃 절에 채워뒀습니다
(Seeed 공식 문서 출처 포함, 하드웨어 담당 확인 대기).

### 2-4. 파싱 노트 좌표 오프셋 — **직접 확인했습니다. 파서가 맞습니다**

`_incoming/parse_d356.py` 를 읽어보니 정규식 `X([+-]\d{6})Y([+-]\d{6})` 를 씁니다.
제가 우려한 문제는 없습니다. `README.md` 의 `[41:49]` 서술이 "X 문자를 포함한 토큰"이라는
뜻이었고, 파서는 애초에 오프셋을 안 씁니다. **문서만 애매했습니다.**

이 항목은 닫습니다. README 문구는 프론트가 정리하겠습니다.

### 2-5. R8 발견에 펌웨어 근거를 하나 붙여주세요

R8은 "회로도에 연결됐는데 코드가 초기화 안 함"입니다. 즉 **코드를 읽었고 그 핀이 없다**는 판정입니다.
그런데 `evidence`에 `kind: "firmware"`가 하나도 없으면 화면이 그 사실을 말할 방법이 없습니다.

지금은 이렇게 처리했습니다.

| 상황 | 화면 |
|---|---|
| 펌웨어 미제출 | `모름` — "펌웨어를 올리면 이 줄이 채워집니다" |
| 펌웨어 제출 + firmware 근거 없음 | `근거 없음` — "펌웨어는 읽었지만, 이 판정은 코드를 근거로 쓰지 않았습니다" |

**틀린 말이 아니라 틀린 말입니다.** 목표 응답을 실제로 화면에 렌더해 보고 확인했습니다 —
R8 카드는 "코드에 D5가 한 번도 나오지 않습니다"라고 주장해 놓고, 바로 아래 코드 레인에서
"이 판정은 코드를 근거로 쓰지 않았습니다"라고 씁니다. **카드가 자기 판정을 부정합니다.**

처음에는 `line: 1`을 억지로 넣는 안을 적어뒀는데, 그건 **없는 줄 번호를 지어내는 것**이라
"숫자를 지어내지 않는다"와 정면으로 충돌합니다. 사용자가 그 줄을 열어봅니다.

**그래서 계약을 고쳤습니다** — `firmware` 근거의 `line`을 `number | null`로 넓혔습니다.
([`API_CONTRACT.md`](../docs/API_CONTRACT.md) "부재도 근거다" 절). 이 모양으로 주세요.

```jsonc
{
  "kind": "firmware",
  "file": "smart_shoe_cabinet_v1.ino",
  "line": null,                       // 가리킬 줄이 없다 = 부재가 근거다
  "snippet": "검사한 파일 1개 · 106줄 · 참조한 핀 3개 (D2 · D3 · D10)\nD5 는 어느 파일에도 나오지 않습니다.",
  "highlight": ["D5"]
}
```

- 프론트는 **이미 양쪽 다 처리합니다.** `line`이 있으면 `파일명 : 줄`, 없으면 파일명만 찍습니다.
- 넓히기만 한 변경이라 기존 응답은 그대로 유효합니다. 이견 있으면 말씀해 주세요 — 되돌립니다.
- 목표 응답 예시에도 반영해 뒀습니다: `docs/examples/check.target-with-firmware.json`의 R08.

### 2-6. R12 근거 문구가 풀다운을 "pull-up" 이라고 적습니다 — **실제 버그**

`_incoming/check.py` 를 실제로 돌려서 확인했습니다. 합성 픽스처를 하나 만들어 넣었습니다:
[`apps/api/tests/fixtures/synthetic-divider-vs-pulldown.d356`](../apps/api/tests/fixtures/synthetic-divider-vs-pulldown.d356)

**먼저 좋은 소식** — 권지효님 Plant Butler 의 `1kΩ + 2kΩ` 분압 토폴로지는
**지금 엔진이 이미 통과시킵니다.** 오탐 없습니다. 직렬 소자가 네트를 끊어서
교차 도메인 조건이 성립하지 않기 때문이고, 우연이 아니라 구조적입니다.

**버그는 문구 쪽입니다.** 저항이 `GND` 로 가는 풀다운인데도 이렇게 나옵니다.

```
[FAIL] R12  net: SIG_A
       U2 (5.0V) drives U1 (3.3V) directly; passives on net: R1 (pull-up, not series)
                                                                 ^^^^^^^ 풀다운입니다
```

원인:

```python
series = [r for r in refs if re.match(r"^(R|D)\d", r)]
... f"passives on net: {','.join(series)} (pull-up, not series)" if series else ...
```

네트에 `R*` 이 있으면 **반대쪽 터미널을 안 보고** 무조건 "pull-up" 이라고 씁니다.

| 저항 반대쪽 | 정체 | 보호되나 |
|---|---|---|
| 상위 전원 (`3V3` · `5V_BUS`) | 풀업 | ❌ |
| `GND` | 풀다운 | ❌ |
| 다른 신호 네트 | 직렬 | ✅ (이때는 네트가 끊겨 R12 후보에 안 옴) |

**판정(FAIL)은 맞습니다. 문구만 고치면 됩니다.** 결론은 풀업이든 풀다운이든 "보호 아님"으로 같습니다.

우리 실제 보드의 R3 는 `3V3` 로 가는 **진짜 풀업**이라 지금 문구가 우연히 맞습니다.
그래서 실제 보드만 돌려서는 이 버그가 안 보입니다. 합성 픽스처를 넣은 이유입니다.

> 근거가 틀리면 판정이 맞아도 신뢰를 잃습니다. 사용자가 "풀업이라고? 나 풀다운 넣었는데"
> 하는 순간 끝입니다. 화면은 이 문구를 **그대로** 사용자에게 보여줍니다.

### 2-2. `firmware` 근거의 `file` 경로 기준

`file: "src/main.cpp"`가 **업로드한 zip 내부의 상대 경로**로 이해하고 그대로 표시하고 있습니다.
맞습니까? 절대 경로나 임시 디렉터리 경로가 섞여 오면 화면에 그대로 노출됩니다.

## 3. 목 데이터 동기화

`apps/web/src/mocks/check.json`은 **실제 보드를 파서·규칙 엔진에 돌린 결과**입니다.
손으로 적은 숫자가 하나도 없고, 앞으로도 손대지 않겠습니다.

엔진 출력이 바뀌면 (규칙 추가 · dedup · 필드 변경)
**새 JSON 파일 하나만 던져주세요.** 프론트가 그대로 교체합니다.

```bash
python -m prefab tests/fixtures/esp32-c6-presence-smart-light.d356 --json > check.json
```

이런 식으로 뽑을 수 있으면 제일 좋습니다.

### 관련 — 알려진 문제 2건이 화면에 보이는 방식

- **R11·R12 중복 검출 ([#1](../../issues/1))** — 지금 목 데이터에 `PRESENCE_3V3`가 두 카드로 뜹니다.
  dedup 되면 발견 수가 3 → 2로 줄 뿐, 화면은 그대로 동작합니다. **기다리겠습니다.**
- **모듈 핀아웃 DB 부재 ([#2](../../issues/2))** — 차별 규칙(R1·R5·R7·R8) 전체의 선행 조건이고,
  화면에서는 발견 카드의 "코드가 아는 것" 레인이 계속 "모름"으로 남습니다.
  그 상태를 숨기지 않고 그대로 보여주고 있으니, 데모에서 불리하지 않습니다.

## ~~0. 로컬에서 프론트-백엔드를 붙일 때 필요한 것~~ — **전부 닫힘**

> 8/18 통합 테스트로 4개 다 확인했습니다. 아래는 기록용으로 남깁니다.

### 0-1. 로컬 실행 방법 한 줄

`uvicorn web.app:app --reload --port 8000`이면 되는지, 다른 준비(환경변수 · API 키)가
있는지만 알려주세요. 붙일 때는 `VITE_API_BASE=http://localhost:8000`을 씁니다.

배포 URL은 **나중에** 주셔도 됩니다. 그때 환경변수만 갈아끼우면 됩니다.

### 0-2. CORS — 지금 넣어주세요

```
허용 origin: http://localhost:5173, <배포 URL — 정해지면 추가>
허용 method: GET, POST, OPTIONS
```

`POST /api/v1/checks`는 `multipart/form-data`라 **프리플라이트(OPTIONS)가 먼저 날아갑니다.**
GET만 열어두면 로컬에서 붙일 때부터 업로드가 통째로 막힙니다.
배포는 미루더라도 이건 지금 넣는 게 쌉니다.

### 0-3. `status: "running"`일 때 `pipeline`을 채워주세요

진행 화면(`/c/{id}`)은 **1초마다 `GET /api/v1/checks/{id}`를 폴링해서 `pipeline` 배열만 그립니다.**

- `status: "running"`이면 → 지금까지 끝난 단계가 실려 있어야 합니다. 나머지는 아직 안 실려도 됩니다.
- `status: "done"`이면 → 프론트가 자동으로 `/r/{id}`로 넘어갑니다.

running인데 `pipeline`이 빈 배열이면 진행 화면이 빈 화면이 됩니다.
검사가 1초 만에 끝난다면 이 항목은 무시하셔도 됩니다 — **그 경우 그렇다고만 알려주세요.**
바로 리포트로 보내도록 화면을 바꾸겠습니다.

### 0-4. 오류 응답 형식 고정

프론트는 `error.message`를 **사용자에게 그대로 보여줍니다.** 따로 문구를 만들지 않습니다.

```json
{ "error": { "code": "NETLIST_REQUIRED", "message": "넷리스트 파일이 필요합니다." } }
```

계약에 있는 4개(`NETLIST_REQUIRED` · `NETLIST_PARSE_FAILED` · `FILE_TOO_LARGE` · `CHECK_NOT_FOUND`)
외에 새 코드가 생기면 알려주세요. 코드를 몰라도 메시지는 뜨지만, 화면에서 다르게 다뤄야 할 게 있을 수 있습니다.

### 2-1. `netlist` 근거에 구조화된 연결 정보

발견 카드의 "회로도가 아는 것" 레인에 **핀-네트 연결을 도식으로 그리려고 합니다.**
지금은 `evidence.text`가 줄바꿈으로 이어진 문자열이라, 그리려면 프론트가 이 문자열을
다시 파싱해야 합니다. 그건 파서를 두 벌 만드는 것이고 계약 위반입니다. 그래서 **안 했습니다.**

제안 (기존 `text`는 그대로 두고 선택 필드로 추가):

```json
{
  "kind": "netlist",
  "text": "U2.OUT → PRESENCE_3V3\nU1.LP-G → PRESENCE_3V3",
  "nodes": [
    { "ref": "U2", "pin": "OUT",  "net": "PRESENCE_3V3", "role": "source" },
    { "ref": "U1", "pin": "LP-G", "net": "PRESENCE_3V3", "role": "sink" }
  ],
  "highlight": ["U2.OUT"]
}
```

- `role`은 `source` / `sink` / `passive` 정도면 충분합니다. 판정에 못 쓰겠으면 빼도 됩니다.
- `nodes`가 없으면 지금처럼 `text`를 그대로 보여줍니다. **없다고 화면이 깨지지 않습니다.**
- **지금 당장은 필요 없습니다.** R7·R8이 돌기 시작해서 코드-회로도 대조가 실제로 나올 때
  같이 넣는 게 맞다고 봅니다.

### 2-3. 넷리스트 핀에 실크 라벨·GPIO를 실어주세요 — **R7·R8의 선행 조건**

이걸 못 하면 R7·R8이 우리 보드에서 못 돕니다. 우선순위 2번에 뒀지만
**R7·R8을 만들기 시작하는 시점에는 이게 먼저 끝나 있어야 합니다.**

픽스처를 파다 확인한 사실입니다.

```
U1 레코드 25개 → 이름 종류 18개
LP-G × 3   (LP_GPIO0 / LP_GPIO1 / LP_GPIO2)
SDIO × 3   (SDIO_DATA1 / DATA2 / DATA3)
```

IPC-D-356이 핀 이름을 4자에서 자르기 때문에 **물리적으로 다른 핀이 같은 이름으로 뭉칩니다.**
그래서 지금 응답으로는 `_IN_ACTIVE_LOW`에 붙은 `U1.SDIO`가 D3인지 D4인지 D5인지 알 수 없습니다.

```jsonc
// 현재
{ "ref": "U1", "pin": "SDIO" }

// 필요
{ "ref": "U1", "pin": "SDIO", "silk": "D5", "gpio": 23 }
```

`parts[].pins`도 같은 문제입니다 — 25개 패드가 18개로 뭉쳐서 D3·D4·D5가 `SDIO` 하나로 보입니다.

**좌표로 풀립니다.** 헤더가 두 열이고 피치가 0.1 inch라서 Y 내림차순이 실크 순서입니다.
대조표를 [`docs/CHIPS.md`](../docs/CHIPS.md) 모듈 핀아웃 절에 채워뒀습니다
(Seeed 공식 문서 출처 포함, 하드웨어 담당 확인 대기).

### 2-5. R8 발견에 펌웨어 근거를 하나 붙여주세요

R8은 "회로도에 연결됐는데 코드가 초기화 안 함"입니다. 즉 **코드를 읽었고 그 핀이 없다**는 판정입니다.
그런데 `evidence`에 `kind: "firmware"`가 하나도 없으면 화면이 그 사실을 말할 방법이 없습니다.

지금은 이렇게 처리했습니다.

| 상황 | 화면 |
|---|---|
| 펌웨어 미제출 | `모름` — "펌웨어를 올리면 이 줄이 채워집니다" |
| 펌웨어 제출 + firmware 근거 없음 | `근거 없음` — "펌웨어는 읽었지만, 이 판정은 코드를 근거로 쓰지 않았습니다" |

**틀린 말이 아니라 틀린 말입니다.** 목표 응답을 실제로 화면에 렌더해 보고 확인했습니다 —
R8 카드는 "코드에 D5가 한 번도 나오지 않습니다"라고 주장해 놓고, 바로 아래 코드 레인에서
"이 판정은 코드를 근거로 쓰지 않았습니다"라고 씁니다. **카드가 자기 판정을 부정합니다.**

처음에는 `line: 1`을 억지로 넣는 안을 적어뒀는데, 그건 **없는 줄 번호를 지어내는 것**이라
"숫자를 지어내지 않는다"와 정면으로 충돌합니다. 사용자가 그 줄을 열어봅니다.

**그래서 계약을 고쳤습니다** — `firmware` 근거의 `line`을 `number | null`로 넓혔습니다.
([`API_CONTRACT.md`](../docs/API_CONTRACT.md) "부재도 근거다" 절). 이 모양으로 주세요.

```jsonc
{
  "kind": "firmware",
  "file": "smart_shoe_cabinet_v1.ino",
  "line": null,                       // 가리킬 줄이 없다 = 부재가 근거다
  "snippet": "검사한 파일 1개 · 106줄 · 참조한 핀 3개 (D2 · D3 · D10)\nD5 는 어느 파일에도 나오지 않습니다.",
  "highlight": ["D5"]
}
```

- 프론트는 **이미 양쪽 다 처리합니다.** `line`이 있으면 `파일명 : 줄`, 없으면 파일명만 찍습니다.
- 넓히기만 한 변경이라 기존 응답은 그대로 유효합니다. 이견 있으면 말씀해 주세요 — 되돌립니다.
- 목표 응답 예시에도 반영해 뒀습니다: `docs/examples/check.target-with-firmware.json`의 R08.

### 2-6. R12 근거 문구가 풀다운을 "pull-up" 이라고 적습니다 — **실제 버그**

`_incoming/check.py` 를 실제로 돌려서 확인했습니다. 합성 픽스처를 하나 만들어 넣었습니다:
[`apps/api/tests/fixtures/synthetic-divider-vs-pulldown.d356`](../apps/api/tests/fixtures/synthetic-divider-vs-pulldown.d356)

**먼저 좋은 소식** — 권지효님 Plant Butler 의 `1kΩ + 2kΩ` 분압 토폴로지는
**지금 엔진이 이미 통과시킵니다.** 오탐 없습니다. 직렬 소자가 네트를 끊어서
교차 도메인 조건이 성립하지 않기 때문이고, 우연이 아니라 구조적입니다.

**버그는 문구 쪽입니다.** 저항이 `GND` 로 가는 풀다운인데도 이렇게 나옵니다.

```
[FAIL] R12  net: SIG_A
       U2 (5.0V) drives U1 (3.3V) directly; passives on net: R1 (pull-up, not series)
                                                                 ^^^^^^^ 풀다운입니다
```

원인:

```python
series = [r for r in refs if re.match(r"^(R|D)\d", r)]
... f"passives on net: {','.join(series)} (pull-up, not series)" if series else ...
```

네트에 `R*` 이 있으면 **반대쪽 터미널을 안 보고** 무조건 "pull-up" 이라고 씁니다.

| 저항 반대쪽 | 정체 | 보호되나 |
|---|---|---|
| 상위 전원 (`3V3` · `5V_BUS`) | 풀업 | ❌ |
| `GND` | 풀다운 | ❌ |
| 다른 신호 네트 | 직렬 | ✅ (이때는 네트가 끊겨 R12 후보에 안 옴) |

**판정(FAIL)은 맞습니다. 문구만 고치면 됩니다.** 결론은 풀업이든 풀다운이든 "보호 아님"으로 같습니다.

우리 실제 보드의 R3 는 `3V3` 로 가는 **진짜 풀업**이라 지금 문구가 우연히 맞습니다.
그래서 실제 보드만 돌려서는 이 버그가 안 보입니다. 합성 픽스처를 넣은 이유입니다.

> 근거가 틀리면 판정이 맞아도 신뢰를 잃습니다. 사용자가 "풀업이라고? 나 풀다운 넣었는데"
> 하는 순간 끝입니다. 화면은 이 문구를 **그대로** 사용자에게 보여줍니다.

### 2-2. `firmware` 근거의 `file` 경로 기준

`file: "src/main.cpp"`가 **업로드한 zip 내부의 상대 경로**로 이해하고 그대로 표시하고 있습니다.
맞습니까? 절대 경로나 임시 디렉터리 경로가 섞여 오면 화면에 그대로 노출됩니다.

### A++1 — 이게 제일 급합니다

IPC-D-356 네트명 필드는 14자인데, kicad-cli 는 **앞을 버리고 뒤를 남깁니다.**

```
원본   unconnected-(U3-SPICLK-Pad22)      ← KiCad 의 "미연결" 표시
d356   -SPICLK-PAD22)                     ← 표시가 사라졌다
```

`esp32-c3-iot-sensor-board` 실측:

```
.kicad_pcb 의 unconnected 네트     32
.d356 에 N/C 로 온 것               2
패드 1개짜리 유사 네트             16    ← 사실 미연결인데 "연결됨"으로 보인다
```

**R07 은 "코드가 쓰는 핀이 회로도에 미연결"입니다.** 차별점의 중심인데,
KiCad 보드에서는 그 핀이 네트에 붙은 것처럼 보여 **조용히 침묵합니다.**
오탐이 아니라 미탐이라 화면에도 안 뜹니다.

우리 픽스처는 Flux 가 `N/C` 로 정직하게 내보내서 이 문제를 한 번도 안 만났습니다.
**C-3(R07) 을 만들기 전에 이게 들어가야 합니다.** 안 그러면 우리 보드에서만 도는 규칙이 됩니다.

**고치는 방법은 이름이 아니라 토폴로지입니다.**

> 패드가 하나뿐인 네트는 이름이 무엇이든 **전기적으로 미연결**입니다.

도구에 무관하고, 절단에도 안 깨지고, 지금 그래프에 이미 있는 정보로 판정됩니다.

### A++2 — 네트 이름 절단

```
+5V_MOTOR_DRIVE_EN  (18자)  →  뒤 14자만 남으면  MOTOR_DRIVE_EN  →  5V 토큰 소실
```

R11 은 네트 이름의 전압 토큰을 읽습니다. 이름이 잘리면 **조용히 미탐**입니다.
우리 픽스처는 `PRESENCE_3V3`(12자)라 안 걸렸습니다.
길이 14에 닿은 네트명은 **절단 의심**으로 표시하고, R11 판정을 UNRESOLVED 로 낮추는 게 맞다고 봅니다.

B-4 는 원래 B-3 뒤였는데 **순서를 뒤집었습니다.** B-3(LLM 추출)은 API 키가 있어야 하고

하면 됩니다.** 그리고 이 순서 덕에 **LLM 없이도 사람이 사실을 채울 수 있는 길**이 생겼습니다.

| 들어간 것 | 어디 |
|---|---|
| `Fact` · `FactSet` — 순수 자료형, IO 없음. **규칙이 보는 것은 이것뿐** | `src/prefab/datasheet/facts.py` |
| `part_facts` SQLite — `checks` 와 **같은 파일** (헌법 9절 "SQLite 한 개") | `src/prefab/datasheet/store.py` |
| 러너 연결 — BOM 부품번호 → 캐시 조회 → `Context.datasheet` | `src/prefab/runner.py` |
| 손으로 채우는 CLI — `python -m prefab --facts-load parts/*.json` | `src/prefab/__main__.py` · `parts/README.md` |

**조회는 러너에서 끝납니다.** 규칙 함수는 DB 를 모릅니다 (헌법 2-1 순수 함수).
`analyze(..., fact_store=...)` 를 안 주면 **지금까지와 완전히 똑같이** 돕니다.

저장기가 두 가지를 **거절**합니다. 헌법 2-2 를 코드가 강제하게 한 것입니다.

- **값이 있는데 `page`·`quote` 가 없으면** 거절합니다. 출처 없는 값은 값이 아닙니다.
- **값이 없는데 `reason` 이 없으면** 거절합니다. "모른다"는 왜 모르는지까지 말해야 합니다.

`value: null` + `reason` 은 거절이 아니라 **정상적인 사실로 저장**합니다.
찾아봤지만 없더라는 것도 사실이고, 저장해 둬야 같은 부품을 두 번 조회하지 않습니다.
`confidence: low` 는 저장은 되지만 `usable` 이 아니라 **판정에 못 씁니다.**

조회 결과는 `hits` / `misses` 로 나옵니다. **`misses` 가 곧 "LLM 을 불러야 할 목록"**이고,
동시에 발표에서 쓸 캐시 적중률입니다.

> **아직 이 사실을 소비하는 규칙이 없습니다.** 그래서 화면은 아무것도 달라지지 않습니다.
> B-4 는 배관이고, 눈에 보이는 것은 B-5 · B-6 에서 나옵니다. 있는 척하지 않겠습니다.

**B-6(R04)을 하실 때 주의할 점이 하나 있습니다.** 규칙이 `needs` 에 `datasheet` 를 선언하려면
**계약(`API_CONTRACT.md`)의 `needs` 어휘를 먼저 넓혀야 합니다.** 지금은 `netlist`·`bom`·`firmware`
세 개로 못박혀 있고, 프론트가 모르는 값이 나가면 화면이 조용히 깨집니다.
엔진 내부(`INPUT_NAMES`)는 이미 `datasheet` 를 알지만, 카탈로그는 일부러 안 건드렸습니다.
`CONTRACT_NEEDS` 와 `test_catalog.py` 가 그 선을 지킵니다. **계약 → 프론트 타입 → 카탈로그 순서**로
가야 합니다.

#### B-5 도 됐습니다 — 이제 **값만 넣으면 화면에서 해제가 일어납니다**

`rules/_clearance.py` 가 R11 · R12 와 사실 DB 사이에 붙었습니다. **비교는 결정적 코드가
합니다.** 데이터시트는 값을 줄 뿐입니다 (헌법 2-1).

사실 하나(`HLK-LD2410C` 의 `voh_max = 3.3V`)를 넣고 실측 보드를 돌린 결과입니다.

| | 넣기 전 | 넣은 뒤 |
|---|---|---|
| 심각 | 2 | **1** |
| 경고 | 1 | 0 |
| **해제** | 0 | **2** |

해제된 발견은 **사라지지 않고** `PASS` 로 남아 출처를 답니다 —
`HLK-LD2410C · Electrical Characteristics p.3: "OUT high level output voltage 3.3V"`.
플래그가 지워지는 순간을 보여주는 게 이 제품의 핵심 경험이라서 그렇습니다.

**요약 집계도 같이 고쳤습니다.** 전에는 해제된 발견이 `cleared` 로도 세어지고
`critical` 로도 세어져서 "심각 1건 · 해제 1건"이 같이 떴습니다. 이제
`critical + warning + cleared` 가 발견 개수와 항상 같습니다. **프론트 확인 부탁드립니다.**

##### 못 풀었을 때가 더 중요합니다

전에는 어떤 경우든 `"U2 미식별 — BOM 필요"` 였습니다. **BOM 을 이미 낸 사람에게는
거짓말입니다.** 이제 끊긴 자리마다 다르게 말합니다.

| 상태 | 미결 사유 |
|---|---|
| BOM 없음 | `BOM 을 제출하면 출력 하이 전압(Voh)을 확인합니다` |
| BOM 은 있는데 그 부품 행이 없음 | `U2 이 BOM 에 없거나 부품번호가 비어 있습니다` |
| 부품번호는 있는데 데이터시트 미수집 | `HLK-LD2410C 의 데이터시트를 아직 읽지 않았습니다` |
| 값은 있는데 출처가 없음 | `출력 하이 전압(Voh) 값에 출처가 없어 판정에 쓰지 않습니다` |
| 확신도 `low` | `확신도가 낮아 판정에 쓰지 않습니다` |
| 데이터시트에 값이 없음 | 데이터시트가 기록한 `reason` 을 그대로 |

##### 질문 자체가 틀린 경우도 막았습니다

`_IN_ACTIVE_LOW` 의 K1 이 그 경우입니다. K1 은 전원 핀을 못 찾아 도메인을 **추론**으로만
아는데, 그러면 **이 네트를 구동하는지 입력으로 받는지도 모릅니다.** `Voh` 는 구동하는
쪽에나 물어볼 값이라, **K1 의 `Voh` 를 알아도 그걸로 해제하지 않습니다.** 잘못된 해제는
오탐보다 나쁩니다. 지금은 이렇게 나갑니다.

> K1이 이 네트를 구동하는지 입력으로 받는지 넷리스트만으로는 알 수 없습니다.
> TONGLING JQC-3FF-S-Z — 핀 방향과 내부 풀업을 확인해야 합니다

같은 이유로 `claim` 이 방향을 단정하던 것도 고쳤습니다 (알려진 버그 4번).
`"K1이 U1을 직접 구동합니다"` → `"K1과 U1이 같은 네트에 직결되어 있습니다"`.

**남은 것**: 핀 방향을 알아내는 길이 없습니다. K1 은 `input_pullup_to` 로 풀리는데
그러려면 규칙이 어느 쪽이 입력인지 알아야 합니다. 지금은 사용자에게 넘깁니다.

### 지켜야 할 선 — LLM 은 결론을 내지 않습니다

```
LLM:     데이터시트 3쪽 표에서 Voh = 3.3V 를 읽어 JSON 으로 반환
결정적:  Voh <= 3.6 비교는 코드가 한다
```

`CLAUDE.md` 2-1 그대로입니다. **LLM 출력이 캐시되어 결정적 자산이 됩니다** — 쓸수록 LLM 의존이 줄어드는 구조이고, 발표에서 이걸 말할 수 있습니다.

### C-2 에서 지금 정해야 하는 것 — 순수 정적 분석인가, AI 추출인가

팀원 코드는 쉬웠습니다.

```c
const int LED_PIN = D10;
pinMode(LED_PIN, OUTPUT);
```

실제 코드는 이렇습니다.

```c
const int pins[] = {2, 3, 10};
for (int i = 0; i < 3; i++) pinMode(pins[i], OUTPUT);
```

배열·조건부 컴파일·라이브러리 래퍼까지 가면 순수 정적 분석은 커버리지가 안 나옵니다. **핀 추출이 틀리면 R07·R08 이 통째로 오탐 생성기가 됩니다.**

AI 로 간다면 안전장치가 필요합니다 — AI 가 **핀 후보 + 근거 위치(파일:줄)** 를 내고, 그 위치에 실제로 그 문자열이 있는지 **결정적으로 확인**하고, 확신 없으면 `UNRESOLVED`.

**나중에 바꾸면 파서를 두 번 만듭니다. 착수 전에 정해 주세요.**

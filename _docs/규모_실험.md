# 규모 실험 — 실제 보드에서 오탐이 어떻게 되나

작성 2026.08.18 · 진행 중

## 왜 하나

지금 우리 픽스처는 **장난감이다.**

| | 우리 픽스처 | 실제 임베디드 보드 |
|---|---|---|
| 네트 | 8 | 50~200 |
| 부품 | 10 | 30~100 |
| 펌웨어 | 파일 1개 · 106줄 | 파일 10~50개 · 수천 줄 |
| 발견 | 3건 | ? |

부품 10개짜리 보드에서도 근거 문구 버그가 **두 개** 나왔다
(풀업/풀다운 오라벨 · 신호 방향 단정). 부품이 5배면 그 이상으로 는다.

**"실생활 수준에서 되는가"는 주장할 수 없고 측정해야 한다.**

## 1단계 결과 — KiCad 없이도 실패가 확인됐다

`.kicad_pcb` 에서 네트-부품 관계를 뽑아 **우리 `signal_nets()` 필터를 그대로** 적용했다.
(`prefab.netlist.graph` 의 `volts()` · `GND_PATTERN` · `POWER_RAIL_FANOUT_MIN` 을 직접 import)

```
실제 보드   네트 46 · 부품 55

접지로 제외       1개  → GND
전원레일로 제외   1개  → +3V3
판정 대상        44개

⚠️ 판정 대상인데 부품 4개 초과 = 전원레일인데 안 걸러짐
      +VSW            부품 9개   volts()=None
      +BATT           부품 8개   volts()=None
      Net-(D5-Pad2)   부품 5개   volts()=None
```

### 원인 — 전원 레일을 **이름으로** 판별한다

`graph.py` `signal_nets()`:

```python
if volts(net) and len(refs) > POWER_RAIL_FANOUT_MIN:
    continue   # 전압 이름 + 팬아웃 많음 = 전원 레일
```

네트 **이름에 전압 토큰이 있는지**로 전원을 판별한다.
우리 보드는 `5V_BUS` · `3V3` 라서 **우연히 맞았다.**

실제 보드는 이렇게 짓는다.

```
+VSW · +BATT · VDD_CORE · AVDD · VREF · VCCIO    ← 전원인데 전압 토큰 없음
SPI_3V3_CS · UART_5V_TX · LED_3V3                ← 신호인데 전압 토큰 있음
```

**둘 다 틀린다.** 전원 레일은 이름이 아니라 **토폴로지**로 판별해야 한다 —
디커플링 캡이 여러 개 붙고, 레귤레이터 출력이고, 붙은 핀이 대부분 `VCC`/`VDD` 인 것.
그 정보를 이미 다 갖고 있는데 이름만 본다.

## 2단계 결과 — 오탐 0건. **그런데 좋은 소식이 아니다**

KiCad 를 설치해 실제로 뽑고 돌렸다.

```bash
kicad-cli pcb export ipcd356 --output vhario.d356 vhario-espc3.kicad_pcb   # 23KB
python -m prefab vhario.d356
```

```
네트 46 · 부품 55
전원 도메인 추론 — 16개 중 14개가 "모름"
발견: 없음   (0건 · 규칙 11개 중 2개 실행)
```

**오탐 0건은 "깨끗하다"가 아니라 "볼 수 없었다"이다.**
R11·R12 는 전원 도메인을 아는 부품이 있어야 발동한다. 16개 중 2개만 알았으니
규칙이 침묵한 것이고, 미탐(false negative) 100% 일 수도 있다.

### 진짜 원인 — 규모가 아니라 **EDA 도구 차이**였다

같은 IPC-D-356 인데 핀 이름이 완전히 다르다.

| | 핀 이름 | 예 |
|---|---|---|
| **Flux** (우리 픽스처) | **이름** | `VBUS` · `GND_` · `UART` · `SDIO` · `LP-G` · `P1` |
| **KiCad** (실제 오픈소스) | **번호** | `1` · `2` · `3` · `4` … (빈 값 127개) |

우리 도메인 추론은 **핀 이름**을 읽는다.

```python
SUPPLY_PIN = re.compile(r"^(VCC|VDD|VIN|VBUS|V\+|5V|3V3|3\.3V|VDDIO)", re.I)
```

KiCad 는 패드 **번호**를 내보내므로 이 정규식이 **한 번도 매치되지 않는다.**
좌표 클러스터링 폴백만 남았고, 그게 16개 중 2개만 건졌다.

### 이게 검증 계획을 위협한다

우리는 재현율을 **오픈소스 레포 30~50개**로 재기로 했다. 그런데 오픈소스 하드웨어는
대부분 **KiCad** 다. 지금 엔진으로 그 레포들을 돌리면 재현율이 0 에 가깝게 나온다 —
**규칙이 나빠서가 아니라 입력을 못 읽어서다.**

8/26 에 이걸 발견했으면 손쓸 시간이 없었다.

### 고칠 방향 — 핀 이름이 아니라 **네트 소속**으로

부품이 어느 네트에 붙어 있는지만 보면 된다. 핀 이름이 필요 없다.

> 어떤 부품의 패드가 `+3V3` 과 `GND` 에 동시에 닿아 있으면 그 부품은 3.3V 부품이다.

실제 보드에 적용해 봤다.

```
레일 후보 네트: ['+3V3', '+BATT', '+VSW']

네트 소속으로 도메인을 알 수 있는 부품   14개  (능동 부품만 세면 J2·U2·U3·U4·U5 = 5개)
지금 엔진이 실제로 알아낸 부품            2개
```

**능동 부품 기준 2개 → 5개.** 그리고 이 방법은 Flux 에서도 그대로 된다 —
우리 보드의 U2 도 `5V_BUS` 와 `GND_BUS` 에 닿아 있다. **양쪽 도구에서 동작한다.**

### 1단계 발견과 같은 뿌리다

`+VSW` · `+BATT` 는 1단계에서 **"전원 레일인데 안 걸러진 것"** 으로 나왔고,
2단계에서는 **"도메인 추론의 열쇠"** 로 나왔다. 같은 네트다.

지금 코드는 이 네트들을 **이름에 전압 토큰이 없다는 이유로** 두 곳 모두에서 놓친다.
`+` 접두사와 팬아웃을 함께 보면 둘 다 풀린다.

## 재현 방법

```bash
curl -sL -o vhario.kicad_pcb \
  https://raw.githubusercontent.com/har-in-air/VhARIO-ESPC3/master/vhario-espc3.kicad_pcb
```

1단계 분석 스크립트는 이 문서의 결과 블록 그대로다 —
`(footprint ...)` 블록마다 `fp_text reference` 로 refdes 를 잡고
그 안의 `(net N "NAME")` 를 모아 네트별 팬아웃을 만든 뒤,
`prefab.netlist.graph` 의 분류 함수를 그대로 적용한다.

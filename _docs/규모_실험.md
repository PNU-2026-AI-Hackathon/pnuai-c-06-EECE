# 규모 실험 — 실제 보드에서 오탐이 어떻게 되나

작성 2026.08.18 · 진행 중

## 왜 하나

지금 우리 픽스처는 **장난감이다.**

| | 우리 픽스처 | 실제 임베디드 보드 |
|---|---|---|
| 네트 | 8 | 50~200 |
| 부품 | 10 | 30~100 |
| 펌웨어 | 파일 1개 · 106줄 | 파일 10~50개 · 수천 줄 |
| 발견 | 3건 | ? |

부품 10개짜리 보드에서도 근거 문구 버그가 **두 개** 나왔다
(풀업/풀다운 오라벨 · 신호 방향 단정). 부품이 5배면 그 이상으로 는다.

**"실생활 수준에서 되는가"는 주장할 수 없고 측정해야 한다.**

## 1단계 결과 — KiCad 없이도 실패가 확인됐다

`.kicad_pcb` 에서 네트-부품 관계를 뽑아 **우리 `signal_nets()` 필터를 그대로** 적용했다.
(`prefab.netlist.graph` 의 `volts()` · `GND_PATTERN` · `POWER_RAIL_FANOUT_MIN` 을 직접 import)

```
실제 보드   네트 46 · 부품 55

접지로 제외       1개  → GND
전원레일로 제외   1개  → +3V3
판정 대상        44개

⚠️ 판정 대상인데 부품 4개 초과 = 전원레일인데 안 걸러짐
      +VSW            부품 9개   volts()=None
      +BATT           부품 8개   volts()=None
      Net-(D5-Pad2)   부품 5개   volts()=None
```

### 원인 — 전원 레일을 **이름으로** 판별한다

`graph.py` `signal_nets()`:

```python
if volts(net) and len(refs) > POWER_RAIL_FANOUT_MIN:
    continue   # 전압 이름 + 팬아웃 많음 = 전원 레일
```

네트 **이름에 전압 토큰이 있는지**로 전원을 판별한다.
우리 보드는 `5V_BUS` · `3V3` 라서 **우연히 맞았다.**

실제 보드는 이렇게 짓는다.

```
+VSW · +BATT · VDD_CORE · AVDD · VREF · VCCIO    ← 전원인데 전압 토큰 없음
SPI_3V3_CS · UART_5V_TX · LED_3V3                ← 신호인데 전압 토큰 있음
```

**둘 다 틀린다.** 전원 레일은 이름이 아니라 **토폴로지**로 판별해야 한다 —
디커플링 캡이 여러 개 붙고, 레귤레이터 출력이고, 붙은 핀이 대부분 `VCC`/`VDD` 인 것.
그 정보를 이미 다 갖고 있는데 이름만 본다.

## 2단계 결과 — 오탐 0건. **그런데 좋은 소식이 아니다**

KiCad 를 설치해 실제로 뽑고 돌렸다.

```bash
kicad-cli pcb export ipcd356 --output vhario.d356 vhario-espc3.kicad_pcb   # 23KB
python -m prefab vhario.d356
```

```
네트 46 · 부품 55
전원 도메인 추론 — 16개 중 14개가 "모름"
발견: 없음   (0건 · 규칙 11개 중 2개 실행)
```

**오탐 0건은 "깨끗하다"가 아니라 "볼 수 없었다"이다.**
R11·R12 는 전원 도메인을 아는 부품이 있어야 발동한다. 16개 중 2개만 알았으니
규칙이 침묵한 것이고, 미탐(false negative) 100% 일 수도 있다.

### 진짜 원인 — 규모가 아니라 **EDA 도구 차이**였다

같은 IPC-D-356 인데 핀 이름이 완전히 다르다.

| | 핀 이름 | 예 |
|---|---|---|
| **Flux** (우리 픽스처) | **이름** | `VBUS` · `GND_` · `UART` · `SDIO` · `LP-G` · `P1` |
| **KiCad** (실제 오픈소스) | **번호** | `1` · `2` · `3` · `4` … (빈 값 127개) |

우리 도메인 추론은 **핀 이름**을 읽는다.

```python
SUPPLY_PIN = re.compile(r"^(VCC|VDD|VIN|VBUS|V\+|5V|3V3|3\.3V|VDDIO)", re.I)
```

KiCad 는 패드 **번호**를 내보내므로 이 정규식이 **한 번도 매치되지 않는다.**
좌표 클러스터링 폴백만 남았고, 그게 16개 중 2개만 건졌다.

### 이게 검증 계획을 위협한다

우리는 재현율을 **오픈소스 레포 30~50개**로 재기로 했다. 그런데 오픈소스 하드웨어는
대부분 **KiCad** 다. 지금 엔진으로 그 레포들을 돌리면 재현율이 0 에 가깝게 나온다 —
**규칙이 나빠서가 아니라 입력을 못 읽어서다.**

8/26 에 이걸 발견했으면 손쓸 시간이 없었다.

### ⚠️ 정정 (2026.08.18) — 처음 적은 수치가 틀렸다

처음에 **"네트 소속으로 보면 능동 부품 도메인이 2개 → 5개"** 라고 적었다. **틀렸다.**

`+BATT` 와 `+VSW` 에 닿은 부품까지 세었는데, 그 레일들은 **전압을 모른다.**

```
+3V3     volts() = 3.3     ← 이름에 전압이 있다
+BATT    volts() = None    ← 3.7V? 4.2V? 알 수 없다
+VSW     volts() = None    ← 레귤레이터 출력. 무엇인지 알 수 없다
```

전압을 아는 레일(`+3V3`)에 GND 와 함께 닿은 부품을 실제로 세어보면:

```
C13 · C15 · C7 · C8 · D7 · U3 · U5      7개
그중 능동 부품:  U3 · U5                 2개  ← 엔진이 이미 찾은 것과 같다
```

**네트 소속 추론을 넣어도 이 보드에서는 능동 부품이 하나도 안 늘어난다.**

### 그래서 진짜 결론은 더 강하다

문제는 핀 이름도, 추론 방식도 아니다.

> **이름에 전압이 없는 전원 레일은 넷리스트만으로 전압을 알 수 없다.**

`+BATT` 가 몇 볼트인지 알려면 배터리 종류를 알아야 하고, `+VSW` 는 그걸 만드는
레귤레이터의 출력 전압을 알아야 한다. **둘 다 부품을 식별해야 나온다.**

즉 이 보드는 **BOM 없이 R11·R12 로 판정할 수 없는 것이 구조적으로 맞다.**
엔진이 침묵한 것은 버그가 아니라 정직한 동작이었다.

**이것이 트랙 B(데이터시트 축)의 근거를 훨씬 강하게 만든다.**
"부품을 알아야 판정이 된다"가 우리 보드 하나의 사정이 아니라 실제 보드의 일반 상황이다.

### 그래도 남는 것

네트 소속 추론(A+1)은 여전히 값이 있다 — 다만 이 보드에서 증명된 건 아니다.
`+5V` · `+3V3` 처럼 **전압이 이름에 있는 레일을 쓰면서 핀은 번호인** 보드에서는
지금의 클러스터 조건(레일과 GND 가 같은 X클러스터에 있어야 함)보다 더 많이 잡는다.
KiCad 보드 상당수가 그렇다. **다른 보드로 확인이 필요하다.**

### 진짜 문제는 리포트가 말하지 않는 것이다

```json
{"critical": 0, "warning": 0, "cleared": 0,
 "parts_identified": 0, "parts_total": 55, "rules_run": 2, "rules_total": 11}
```

**발견 0건이 화면에서 "이상 없음"처럼 보인다.** 실제로는 부품 55개 중 0개를 식별했고
규칙 11개 중 2개만 돌았다. 사용자는 "내 보드 깨끗하네"로 읽는다.

`CLAUDE.md` 2-4 — 못 한 일을 숨기지 않는다. **이건 숨기는 것이다.**
발견이 0건일 때 그것이 "검사했고 깨끗함"인지 "볼 수 없어서 못 찾음"인지
화면이 구분해서 말해야 한다.

### 1단계 발견과 같은 뿌리다

`+VSW` · `+BATT` 는 1단계에서 **"전원 레일인데 안 걸러진 것"** 으로 나왔고,
2단계에서는 **"도메인 추론의 열쇠"** 로 나왔다. 같은 네트다.

지금 코드는 이 네트들을 **이름에 전압 토큰이 없다는 이유로** 두 곳 모두에서 놓친다.
`+` 접두사와 팬아웃을 함께 보면 둘 다 풀린다.

## 왜 `vhario.d356` 을 리포에 커밋하지 않는가

VhARIO-ESPC3 은 **GPL-3.0** 이다. 그 설계에서 뽑은 넷리스트는 파생물로 볼 여지가 있고,
우리 리포는 MIT 다. **라이선스가 섞이면 안 되므로 파일을 넣지 않는다.**

대신 두 가지를 넣었다.

1. **재현 방법** (아래) — 누구나 같은 파일을 다시 만들 수 있다
2. **합성 픽스처 테스트** — `tests/test_d356.py` 에 KiCad 식 레코드(`367`)를
   인라인 문자열로 넣어 회귀를 막는다. 남의 저작물이 아니다

## 재현 방법

```bash
curl -sL -o vhario.kicad_pcb \
  https://raw.githubusercontent.com/har-in-air/VhARIO-ESPC3/master/vhario-espc3.kicad_pcb
```

1단계 분석 스크립트는 이 문서의 결과 블록 그대로다 —
`(footprint ...)` 블록마다 `fp_text reference` 로 refdes 를 잡고
그 안의 `(net N "NAME")` 를 모아 네트별 팬아웃을 만든 뒤,
`prefab.netlist.graph` 의 분류 함수를 그대로 적용한다.

## A+1 닫힘 (2026-08-19) — 다만 원인이 예상과 달랐다

이 문서는 `+VSW` · `+BATT` 를 못 걸러낸다고 적었다. **그건 그 사이에 고쳐졌다** —
`POWER_NAME_PATTERN` 이 `+` 접두사와 `VSW` · `VBAT` 를 잡는다.

실제 보드 세 개(우리 것 · esp32-c3-iot-sensor-board · esp32-laser-security)로 다시 재보니
남아 있던 것은 다른 것이었다.

```
/GND  →  접지로 인식이 안 됐다
```

KiCad 는 계층 시트를 쓰면 네트 이름 앞에 경로를 붙인다. 이름 패턴이 `^` 로 시작하므로
`/GND` 가 어떤 패턴에도 안 걸리고 **신호 네트로 분류됐다.** 그 위에 도는 규칙이 전부 흔들린다.

Flux 로 만든 우리 픽스처는 경로가 없어서 이 문제를 한 번도 못 만났다. **A++1(미연결) ·
A++2(네트명 절단)과 같은 종류다** — 도구가 바뀌면 이름의 모양이 바뀐다.

### 이름 없이도 서는 근거를 넣었다

이름은 양쪽으로 틀린다. `V_LDO` 는 전원인데 전압 토큰이 없고 `PRESENCE_3V3` 는 신호인데 있다.
그래서 토폴로지를 먼저 본다.

1. 공급 핀(`VCC`·`VDD`…)이 **둘 이상** 붙어 있다
2. **접지로 가는 커패시터**가 있고 이름도 레일이라고 말한다 (디커플링)
3. 이름이 레일 같고 팬아웃이 넓다 (기존)

세 보드로 검증했다 — **우리 보드와 c3v4 는 판정이 하나도 안 바뀌었고**, laser 의 `/GND`
하나가 고쳐졌다. 회귀 없이 진짜 버그만 닫혔다.

### 그래도 발견은 여전히 0건이다

이 수정으로 **분류는 맞아졌지만 판정은 아직 안 된다.** 세 보드의 부품 도메인을 여전히
모르기 때문이다 — KiCad 는 핀을 번호로 내보내고, 그래서 어느 핀이 `VCC` 인지 모른다.

> **`+BATT` 가 몇 볼트인지 알려면 배터리를 알아야 한다.**

즉 남은 것은 A+1 이 아니라 **부품 식별(트랙 B)** 이다. 이 문서가 처음부터 그렇게 적었고,
이번 측정이 그 결론을 한 번 더 확인했다.

## A(E-1) 닫힘 (2026-08-19) — 정답이 존재하지 않는다

E-1 의 설계는 이랬다. **LLM 이 "핀을 고친 커밋" 후보를 내고, 코드가 그 diff 를 열어
실제로 그 핀이 바뀌었는지 확인한다.** 개발자 자신의 수정 커밋이 정답이므로 우리가
정답을 지어내지 않는다 — 그게 이 방식을 고른 이유였다.

그 정답이 표본에 없다.

### 세어 봤다

표본 81쌍 전체의 커밋 메시지 **5,299건**을 훑었다.

| 단계 | 남은 수 | 무엇을 걸렀나 |
|---|---|---|
| 전체 커밋 | 5,299 | — |
| 핀·배선 수정을 말하는 메시지 | 46 | 정규식 (29개 레포) |
| 펌웨어 파일을 건드린 것 | 14 | 21건은 회로도·거버만 고쳤다 |
| **핀 배정이 실제로 바뀐 것** | **2** | diff 를 열어 코드가 확인 |

메시지가 핀을 말한 46건 중 44건은 핀을 안 바꿨다. footprint 교체, 솔더마스크 여백,
KiCad 플로터 리팩터링이었다. **메시지는 근거가 아니다** — 그래서 diff 를 열게 설계한 것이고,
그 단계가 실제로 일했다.

### 남은 2건도 정답이 못 된다

```
jkramarz/TheTick        1167e49   pins_arduino.h : SDA 8 → 6
tomtor/STM32-RFM95-PCB  90644cd   analogRead(PIN_PA3) → PIN_PD1
```

- **둘 다 회로도를 안 건드렸다** (변경 파일 7개·1개 중 `.kicad_sch` 0개).
  회로도가 반대로 말했다는 증거가 없으니 "회로도 ↔ 코드 어긋남"의 사례가 아니다.
  그냥 펌웨어 안에서의 변경이다.
- 둘 다 **GPL-3.0** 이다. 보드 파일을 이 저장소에 못 넣는다 (기존 방침).
- TheTick 의 것은 버그 수정이 아니라 **보드 배리언트 정의 파일**이다. tomtor 는 STM32라
  칩 표에 없다.

### 왜 없는지가 핵심이다

취미 저장소는 **회로도와 펌웨어를 같은 커밋에 안 담는다.** 보드를 고치고 한참 뒤에
코드를 고치거나, 아예 코드만 고친다. 우리가 잡으려는 결함은 정의상 그 둘 사이에 있는데,
그 사이가 이력에 안 남는다.

> **우리가 푸는 문제가 희귀해서가 아니라, 그 문제가 커밋으로 안 남기 때문이다.**

이건 제품에는 오히려 유리한 사실이고(아무도 기록을 안 남기니 아무도 못 잡는다),
측정에는 불리한 사실이다. 두 가지를 같이 적어 둔다.

### 그래서 B 로 간다

E-1 은 여기서 닫는다. 되살리려면 표본이 아니라 **정답의 출처**를 바꿔야 한다
(이슈 트래커 · 포럼의 "왜 안 되죠" 글). 지금 11일에 할 일이 아니다.

대신 **R07·R08 을 실제 보드에 돌린다.** 이 둘은 칩 표도 도메인도 안 거치므로
부품 식별(트랙 B)이 막혀 있어도 판정이 나온다.

## B — R07·R08 을 실제 보드 3개에 돌렸다 (2026-08-19)

A 를 닫으면서 "R07·R08 은 칩 표도 도메인도 안 거치니 실보드에서 판정이 날 것"이라고
적었다. **그 예상이 틀렸다.** 돌려 보고 알았다.

### 무엇에 돌렸나

우리가 안 만든 보드 3개다. 도구도 칩도 다르다.

| 보드 | 칩 | 부품 | 패드 | 펌웨어 | 라이선스 |
|---|---|---|---|---|---|
| `Ans1S/esp32-c3-iot-sensor-board` V4 | ESP32-C3 | 49 | 170 | 3,035줄 | MIT |
| `JaswantBhartiya/esp32-laser-security` | ESP32 | 11 | 31 | 1,380줄 | MIT |
| `emertcakir/OpenAirScope` | **STM32H7** | 262 | 927 | 2,500줄 | MIT |

셋 다 `kicad-cli pcb export ipcd356` 로 우리가 직접 뽑았다. 보드 파일은 저장소에 안 넣는다.

### 결과 — 0건. 그리고 그게 옳다

```
c3v4      R07 0건 · R08 0건    parts_identified 0 / 49
laser     R07 0건 · R08 0건    parts_identified 0 / 11
airscope  R07 0건 · R08 0건    parts_identified 0 / 262
```

정답을 엔진과 따로 셌다 — 원본 `.d356` 에서 고립 패드 16·0·55개, `N/C` 표시 2·7·6개가
나온다. **놓친 것이 분명히 있다.**

### 왜 0인지 — 실크 이름이 없다

`pinmap` 이 만드는 GPIO 패드 수를 재 봤다.

| | GPIO 패드 |
|---|---|
| 우리 보드 (Flux 수출) | **11** |
| c3v4 · laser · airscope (KiCad 수출) | **0 · 0 · 0** |

Flux 는 패드에 실크 이름을 싣는다 (`D2` · `5V`). KiCad 는 **번호만** 싣는다
(`A1` · `4` · `19`). R07 은 펌웨어의 `GPIO4` 를 보드의 어느 패드인지 짚어야 하는데,
번호만으로는 못 짚는다.

> **R07·R08 은 칩 표에 안 매여 있는 게 맞다. 하지만 부품 식별에는 매여 있다.**
> 그 둘을 내가 같은 것으로 뭉뚱그렸다. 아니었다.

즉 A+1 이 내린 결론과 **같은 벽이다.** 막힌 곳이 여러 개가 아니라 하나다 —
**부품 식별(트랙 B).** 이번 측정이 그걸 좁혀 확인했다.

### 두 번째 구멍 — 펌웨어 상수를 못 푼다

이건 별개고 더 작다.

| 보드 | 코드의 핀 호출 | 파서가 푼 핀 |
|---|---|---|
| c3v4 | 43 | 2 |
| laser | 68 | 7 |
| airscope | 51 | **0** |

실제 코드는 `digitalWrite(BUZZER_PIN, …)` 처럼 **이름**을 쓴다. 정의(`const int BUZZER_PIN = 5;`)가
다른 파일에 있으면 못 따라간다. airscope 는 STM32 HAL(`HAL_GPIO_WritePin(PORT, PIN, …)`)이라
아예 한 개도 못 읽는다 — 파서가 Arduino·ESP-IDF 말만 안다.

부품 식별이 풀려도 이게 남는다. 다만 **순서는 부품 식별이 먼저다** (그게 안 풀리면
상수를 다 풀어도 0건이다).

### 진짜 성과는 0건이 아니라 그 옆에 붙은 말이다

우리가 안 만든 보드, 안 쓰는 도구, 칩 표에 없는 칩(STM32H7)에서 엔진이
**조용히 0건을 내지 않았다.** 파이프라인이 그대로 말한다 —

```
· [partial] 부품 식별        BOM 없음 · 좌표 클러스터링으로 전원 도메인만 추정
· [partial] 펌웨어 정적 분석  소스 8개 · 3,035줄 · 코드가 쓰는 핀 2개
                            · 회로도에서 못 짚은 핀 2개
                            · 못 읽은 자리 25곳 (정의를 못 찾은 상수 25곳)
  [done]   규칙 엔진         11개 중 10개 실행 · 미구현 0 · 입력 부족 1
           요약              parts_identified 0 / 49
```

**모르는 것을 아는 척하지 않았고, 왜 모르는지를 숫자로 댔다** (CLAUDE.md 2-1 · 2-2).
처음 보는 보드에서 이게 유지되는 것을 확인한 건 이번이 처음이다.
"0건 = 문제 없음"으로 읽힐 자리를 제품이 스스로 막았다.

### 남은 일의 순서가 정해졌다

1. **부품 식별 (트랙 B)** — 이게 유일한 병목이다. BOM 이 있으면 풀리는지부터 확인한다.
2. 펌웨어 상수의 **파일 간 해석**
3. STM32 HAL 문법 (마감 전에는 안 한다 — 우리 대상 칩이 아니다)

## 되짚기 — "긁어온 게 완성품이라 그런 것 아니냐" (2026-08-19)

팀장이 A·B 결과를 보고 물었다. **A 에 대해서는 이 지적이 위에 적은 내 설명보다 낫다.**
B 에 대해서는 아니고, 그건 실험으로 갈렸다.

### A — 생존 편향이 더 근본이다

위에서 "취미 저장소는 회로도와 펌웨어를 같은 커밋에 안 담는다"라고 적었다.
그건 증상이고 원인은 따로 있다 — **깃허브에 올라온 보드는 작동해서 올라온 보드다.**
고치는 과정은 책상 위에서 끝나고 커밋으로 안 남는다.

5,299건 중 2건이라는 수확은 **결함이 희귀해서가 아니라 표본이 구조적으로 결함을
담을 수 없어서**다. 이건 방법의 실패가 아니라 데이터 출처의 실패다.

> **공개 저장소는 검증 데이터가 될 수 없다.**
> 필요한 건 "완성 전" 상태인데, 그게 남는 저장소가 아니다.

그래서 남은 기간의 검증 대상은 **진행 중인 보드** — 우리 보드와 팀원 보드다.

### B — 그 설명이 안 통한다. 통제 실험으로 확인했다

완성품 가설은 *엔진이 분석을 끝낸 뒤* 0건을 예측한다. 관측된 것은
*분석이 시작도 못 해서* 0건이다 (`parts_identified 0/49` · `pinmap GPIO 패드 0`).

가르기 위해 **우리 보드**로 통제 실험을 했다. 결함이 있는 것을 아는 보드다.
네트·좌표·연결은 한 글자도 안 건드리고 **핀 이름 필드 `[27:31]` 만** KiCad 처럼
일련번호로 바꿨다.

| | pinmap GPIO 패드 | 발견 |
|---|---|---|
| 원본 (Flux · 실크 이름 `D2`) | **11** | **5건** — R07×2 · R08 · R12×2 |
| 대조 (핀 이름만 번호 `1`) | **0** | 2건 — R07·R08·R12 전멸 |

같은 보드·같은 펌웨어·같은 BOM. 결함은 그대로 있는데 **엔진이 못 본다.**
스크립트는 `scratchpad/strip_silk.py` 에 있다 (보드 파일은 저장소에 안 넣는다).

### 그래서 정확히 말하면

- 실보드 3개에 결함이 있는지는 **여전히 모른다.** 판정을 못 했으니 모른다.
- 못 한 이유는 **확실히 포맷이다.** 그것만 바꿔서 재현했으니 확실하다.

두 문장을 붙여 쓰지 않는 것이 중요하다. "실보드에서 0건" 을 성능으로도,
무능으로도 읽으면 둘 다 틀린다. **우리는 아직 그 질문에 답할 자격을 못 얻었다.**

## 완성 전 상태를 긁어올 수 있나 — 있었다. 그리고 벽의 정체가 드러났다 (2026-08-19)

팀장이 물었다. "완성 전 커밋들까지 못 긁어오나? 그럼 오류가 무조건 있잖아."

### 있다. 커밋보다 좋은 형태로 있었다

`Ans1S/esp32-c3-iot-sensor-board` 는 **V1·V2·V3·V4 를 트리에 다 갖고 있다.**
깃 고고학이 필요 없다. (그 저장소의 커밋은 13개고 전부 "Initial commit" 에 쏟아져 있다 —
생존 편향의 교과서적 사례다.)

넷을 다 뽑아 MCU 의 GPIO → 네트 대응을 비교했다.

| GPIO | V1 | V2 | V3 | V4 |
|---|---|---|---|---|
| 3 | **unconnected** | VCC_Sensor | ADC | ADC |
| 8 | TD | GPIO8 | GPIO8 | GPIO8 |
| 10 | TMR | **unconnected** | VCC_Sensor | SENSOR_PWR_EN |

펌웨어(HEAD)는 `adcPin = 3` 으로 `analogRead`, `sensorVccPin = 10` 으로 `digitalWrite` 한다.
**V1 은 GPIO3 이, V2 는 GPIO10 이 미연결이다** — R07 이 잡으라고 만든 바로 그 모양이다.

### 다만 이것은 라벨이 아니다

그 저장소의 펌웨어 커밋은 2개뿐이고 **리비전별 펌웨어가 없다.**
V1 보드에 HEAD 펌웨어를 짝지은 것은 **개발자가 아니라 우리다.**

- 개발자 자신의 기록으로 확실한 것: **보드에서 GPIO3·GPIO10 이 옮겨 다녔고 초기엔 미연결이었다.**
- 확실하지 않은 것: 그 시절 펌웨어가 그 핀을 썼는지.

그러니 "남의 저장소에서 진짜 버그를 찾았다" 고 쓰면 안 된다. **현실적인 입력**이지
**라벨된 결함**이 아니다. 이 구분을 지키는 것이 이 프로젝트다.

### 진짜 소득 — 벽이 입력 형식이었다

V1~V4 를 IPC-D-356 으로 뽑아 엔진에 넣으면 **넷 다 0건**이다 (pinmap 0).
그런데 같은 회로도를 `kicadxml` 로 뽑으면 이렇다.

```
kicad-cli sch export netlist --format kicadxml -o out.xml board.kicad_sch
```

| 같은 보드에서 얻는 것 | IPC-D-356 | kicadxml |
|---|---|---|
| 부품번호 (LCSC·MPN) | 0% | **100%** (52/52) |
| 데이터시트 URL | 0% | **100%** |
| 핀 이름 | **0%** (번호만) | **62%** (115/183) |

```
U3.8   GPIO3_8      → ADC
U3.16  GPIO10_16    → SENSOR_PWR_EN
U3.28  U0TXD_28     → unconnected-(U3-U0TXD-Pad28)
U3.22  SPICLK_22    → unconnected-(U3-SPICLK-Pad22)
```

**부품 식별·데이터시트 조회·핀 이름이 한 번에 풀린다.** 세 개를 따로 뚫을 일이 아니었다.
IPC-D-356 은 제조용 파일이라 사람이 읽는 이름을 안 싣는다 — 우리가 판정에 필요한 것이
바로 그 이름이다. 처음부터 형식을 잘못 골랐다.

우리 보드가 되던 이유도 이걸로 설명된다 — **Flux 는 IPC-D-356 에 실크 이름을 실어 준다.**
그래서 한 도구에서만 되는 걸 모르고 지나갔다.

### 그래서 다음 순서

1. **`kicadxml` 리더** — `Netlist` 를 그대로 만들어 내는 두 번째 입력 형식.
   좌표가 없으므로 좌표 기반 전원 도메인 추정은 못 쓰지만, 핀 이름이 그보다 낫다.
2. 그다음에 이 리비전 코퍼스(V1~V4)로 **R07·R08 회귀 측정**을 돌린다.
   라벨이 아니라 "현실적인 입력에서 안 죽는가" 를 본다.
3. BOM 경로는 후순위다 — kicadxml 이 부품번호를 100% 실어 준다.

## kicadxml 리더 — 벽이 뚫렸다 (2026-08-19)

BOM 확인은 **안 했다.** 할 필요가 없었기 때문이다 — 통제 실험이 이미 답을 갖고 있었다.
그 실험은 **양쪽 arm 에 BOM 을 다 넣었다.**

```
원본   + BOM → pinmap 11 · 부품식별 3/10 · 발견 5건
번호만 + BOM → pinmap  0 · 부품식별 3/10 · 발견 2건
```

BOM 이 있는데도 pinmap 이 0 으로 떨어졌고 부품 식별 수치는 양쪽이 같다.
**BOM 은 자기 일(부품↔부품번호)을 하지만 핀 이름을 안 실어서 R07·R08 을 못 살린다.**
데이터시트 조회용으로도 kicadxml 이 MPN·URL 을 100% 주므로 대체된다.

### 만든 것

`src/prefab/netlist/kicadxml.py` — 회로도 넷리스트를 `Netlist` 로 읽는 두 번째 입력 형식.
`Pad.name` (핀 이름) 필드를 더했고, `pinmap._bare_chip` 이 **이름이 있으면 이름을** 본다.
변경은 그게 전부다. 규칙 코드는 한 줄도 안 건드렸다.

심볼 라이브러리가 이름 끝에 핀 번호를 붙여 두는 규약(`GPIO3_8`)은 **번호와 정확히
맞을 때만** 뗀다. 실측한 두 저장소 모두 100% 그 규약이었지만, 다른 도구에서
이름 끝을 잘라먹지 않기 위해서다.

### 결과 — pinmap 0 → 7

리비전 4개 전부에서 GPIO 패드 `[2, 3, 8, 9, 10, 18, 19]` 가 풀린다.
그리고 R07 이 **보드가 고쳐지는 것과 발맞춰 움직인다.**

| | V1 | V2 | V3 | V4 |
|---|---|---|---|---|
| GPIO3 (`analogRead`) | **미연결** | VCC_Sensor | ADC | ADC |
| GPIO10 (`digitalWrite`) | TMR | **미연결** | VCC_Sensor | SENSOR_PWR_EN |
| **R07** | **1건** | **1건** | 0건 | 0건 |
| R08 | 5건 | 5건 | 5건 | 5건 |

V1 은 GPIO3 을, V2 는 GPIO10 을 정확히 짚었고 배선이 붙은 V3·V4 에서는 조용하다.
**엔진이 우리가 안 만든 보드에서 처음으로 말을 했다.**

여전히 지켜야 할 선 — 그 저장소는 펌웨어 커밋이 2개뿐이라 리비전별 펌웨어가 없다.
V1 보드에 HEAD 펌웨어를 짝지은 것은 **우리다.** 그러니 "개발자의 버그를 재현했다" 가
아니라 **"현실적인 입력에서 규칙이 배선을 따라 켜지고 꺼진다"** 까지가 말할 수 있는 전부다.

### 덤으로 오탐 하나를 찾았다 — R08 의 USB 핀

R08 이 네 리비전 내내 5건으로 고정인데 그 안에 `USB_D+` · `USB_D-` 가 있다.

```
[R08] U3.GPIO18 (GPIO18, 패드명 25) → USB_D-
[R08] U3.GPIO19 (GPIO19, 패드명 26) → USB_D+
```

**USB 는 GPIO 코드가 아니라 USB 주변장치가 몬다.** 펌웨어에 `pinMode(18, …)` 이
없는 게 정상이다. 이건 오탐이고, 우리 픽스처에는 USB 를 뽑아 쓰는 보드가 없어서
한 번도 안 만났다 — **A++1 · A++2 · GPIO16 과 같은 종류다** (도구·보드가 바뀌면
전제가 바뀐다). 규칙에 "주변장치 전용 핀" 개념이 없다.

고치는 것은 다음 일이다. 여기서는 **찾았고 안 숨겼다** 는 것만 기록한다.

### 남은 순서

1. **업로드 경로에 형식 감지를 붙인다** — 지금 리더는 엔진 안에만 있고 사용자가 못 쓴다.
2. R08 의 주변장치 전용 핀 (USB·XTAL) 오탐
3. 부품번호 100% 를 사실 DB 조회에 연결 (BOM 없이도 데이터시트가 붙는다)

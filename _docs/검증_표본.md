## 파이프라인 실증 — 변환은 된다. **판정은 안 된다**

MIT 보드 둘을 실제로 태웠다. `kicad-cli 10.0.5`.

```bash
kicad-cli pcb export ipcd356 --output board.d356 board.kicad_pcb
python -m prefab board.d356
```

| 보드 | 파싱 | 도메인 추론 | 발견 |
|---|---|---|---|
| esp32-c3-iot-sensor-board V4 | 네트 52 · 부품 49 ✅ | **49개 중 2개** | **0건** |
| esp32-laser-security | 네트 11 · 부품 11 ✅ | **11개 중 0개** | **0건** |
| (규모_실험) VhARIO-ESPC3 | 네트 46 · 부품 55 ✅ | 16개 중 2개 | 0건 |

**세 보드 연속 0건이다.** 우연이 아니라 구조적이다.

### 원인이 셋 다 같다 — 핀이 이름이 아니라 번호로 온다

```
c3v4     숫자형 핀 148/170
laser    숫자형 핀  31/31
```

도메인 추론이 읽는 정규식은 이름을 본다.

```python
SUPPLY_PIN = re.compile(r"^(VCC|VDD|VIN|VBUS|V\+|5V|3V3|3\.3V|VDDIO)", re.I)
```

KiCad 는 패드 **번호**(`1` `2` `3`)를 내보내므로 **한 번도 매치되지 않는다.**
Flux 로 만든 우리 픽스처만 이름(`VBUS` `GND_` `UART`)이 나온다.

> **표본을 81개로 늘려도 지금 엔진으로는 전부 0건이다.**
> A+1 · A+2(이름 대신 토폴로지로 전원 레일 판별)가 검증의 선행 조건이다.

### 새로 확인한 것 ① — **R07 이 KiCad 보드에서 발동하지 않는다**

절단은 앞을 버리고 **뒤 14자를 남긴다.**

```
원본   unconnected-(U3-SPICLK-Pad22)     ← KiCad 의 "미연결" 표시
d356   -SPICLK-PAD22)                    ← 표시가 통째로 사라졌다
```

`c3v4` 실측:

```
.kicad_pcb 의 unconnected 네트     32
.d356 에 N/C 로 온 것               2
패드 1개짜리 유사 네트             16   ← 사실은 미연결인데 "연결됨"으로 보인다
```

**R07 은 "코드가 쓰는 핀이 회로도에 미연결"을 잡는다.** 우리 차별점의 중심이다.
그런데 KiCad 보드에서는 그 핀이 `-SPICLK-PAD22)` 라는 이름의 네트에 **연결된 것으로 보인다.**
R07 은 조용히 침묵한다. 오탐이 아니라 **미탐**이라 화면에도 안 나온다.

Flux 로 만든 우리 픽스처는 미연결을 `N/C` 로 정직하게 내보내서 이 문제를 못 만났다.

**고치는 방법은 이름이 아니라 토폴로지다.**

> **패드가 하나뿐인 네트는 이름이 무엇이든 전기적으로 미연결이다.**

도구에 무관하고, 절단에도 안 깨지고, 지금 그래프에 이미 있는 정보로 판정된다.

### 새로 확인한 것 ② — 네트 이름도 잘린다

IPC-D-356 의 네트명 필드는 14자다. 핀 이름만 잘리는 게 아니었다.

```
-(U4-NTC-PAD8)      ← 원본은 Net-(U4-NTC-PAD8) 류
-SPICLK-PAD22)
3-SPIHD-PAD19)
```

**R11 이 네트 이름의 전압 토큰을 읽는다.** 이름이 잘리면 조용히 틀린다.

```
+5V_MOTOR_DRIVE_EN  (18자)  →  잘리면 5V 토큰이 사라진다  →  R11 미탐
```

우리 픽스처는 이름이 짧아서(`PRESENCE_3V3` 12자) 이 문제를 한 번도 못 만났다.
**A-6 으로 요청서에 올려야 한다.**

## 건진 것 — `esp32-laser-security` 는 실제 드리프트 사례다

MIT · ESP32 · 넷리스트와 펌웨어가 같은 레포. **우리 보드가 아닌 곳에서 처음 나온 후보다.**

넷리스트 (J2 = ESP32 모듈 헤더):

```
/D34 : J2.1  R1.2 R2.2      ← 분압 (R1→3V3, R2→GND). LDR 입력
/D18 : J2.2  SW1            ← 스위치
/D5  : J2.3  J3.1           ← 커넥터
/D4  : J2.4  R6.2           ← R6 → D1.A2
/D2  : J2.5  R3.2 R4.2      ← R4 → D1.A1
```

펌웨어 (`src/testing/laser-connected-esp.cpp`):

```c
const int LASER_PIN  = 4;    pinMode(LASER_PIN,  OUTPUT);
const int BUZZER_PIN = 5;    pinMode(BUZZER_PIN, OUTPUT);
const int LDR_PIN    = 34;   pinMode(LDR_PIN,    INPUT);
const int RESET_PIN  = 18;   pinMode(RESET_PIN,  INPUT_PULLUP);
```

| 핀 | 회로도 | 코드 | 판정 후보 |
|---|---|---|---|
| D34 | 분압 입력 | `INPUT` | **음성 케이스** — GPIO34 는 입력 전용이고 입력으로 썼다. R1 이 뜨면 오탐 |
| D18 · D5 · D4 | 배선됨 | 사용함 | 정상 |
| **D2** | **D1 로 배선됨** | **어디에도 안 나옴** | **R08 후보** |

D1 은 3핀 소자이고 A1(D2 경유)·A2(D4 경유) 두 애노드를 갖는다. 즉 **2색 LED 를 D2·D4 로
구동하는 회로인데, 코드는 D4 를 "레이저"로 알고 D2 는 건드리지 않는다.**

주의 — 이 레포의 `src/main.cpp` 에는 `pinMode` 가 없고 핀 정의는 `src/testing/` 에만 있다.
**어느 파일이 "그 보드의 펌웨어"인지 애매하다.** 실제 픽스처로 승격하려면 이 판단이 먼저다.

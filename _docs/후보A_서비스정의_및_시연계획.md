## 0. 한 문장

> **이미 짜놓은 펌웨어가 바뀐 회로도를 따라가고 있는지** 검사하는 에이전트.
> 회로도·펌웨어·데이터시트를 함께 읽고, 셋 사이의 어긋남을 **보드 발주 전에** 잡는다.

### 왜 "드리프트"인가 (2026.08.16 재정의)

기존 도구들은 전부 **한 방향, 한 번**입니다. 우리는 **양방향, 계속**입니다.

| 기존 도구 | 하는 일 | 안 하는 일 |
|---|---|---|
| STM32CubeMX, esp32pin.com | 칩 규칙을 **표로** 보여줌 | 사용자 파일을 안 읽음 |
| Traceformer, AllSpice DRCY | 회로도 검토 | 펌웨어를 안 읽음 |
| **Flux Copilot Firmware** | **회로도 → 초기 코드 생성 (한 방향)** | **이미 있는 코드를 회로도와 대조하지 않음** |
| Flux AI Design Review | 회로도 6종 검사 (데이터시트 참조) | 펌웨어를 안 봄 |
| Embedder | 펌웨어 코드 | 회로도를 안 봄 |
| **Prefab** | **기존 코드 ↔ 현재 회로도 대조 (계속)** | — |

**핵심 메시지 (발표에서 이 문장을 씁니다)**

> Flux는 회로도로 **새 코드를 만들어 줍니다. 한 번 씁니다.**
> 우리는 회로도와 코드가 **시간이 지나며 어긋나는 걸 잡습니다. 계속 씁니다.**

Rev A에서 Rev B로 배선을 고치고 코드를 안 고치는 일은 임베디드 하는 사람이면 다 겪습니다.
**Flux Copilot으로 초기 코드를 생성한 팀일수록 더 겪습니다** — 처음 한 번은 자동으로 맞았으니 그 뒤로 안 보거든요.

### 이 재정의가 사업 구조를 바꿉니다

일회성 검사 → **PR마다 도는 CI 검사**. 반복 사용이 생기고 반복 매출이 생깁니다.
로드맵으로 미뤄뒀던 GitHub Action이 **이제 제품의 본체**입니다.

## 1. 왜 이 문제인가

임베디드에서 가장 비싼 버그는 컴파일도 되고 업로드도 되는 버그입니다.

- 코드는 정상 컴파일 → 컴파일러가 못 잡음
- 회로도는 DRC 통과 → EDA 툴이 못 잡음
- 문제는 **둘 사이**에 있음 → 아무 도구도 안 봄
- 발견 시점: 보드가 도착해서 안 켜질 때
- 비용: 디버깅 반나절~며칠 + 리스핀 시 **2주 + 수십만 원**

**사회적 연결**: 오픈소스 보조공학 하드웨어(장애인 보조기기) 메이커들은 회로 검토를 해줄 사람이 없어서 이 비용을 그대로 떠안습니다. 우리 검증 데이터셋을 이 레포들로 잡으면 검증과 서사가 같은 일이 됩니다. (억지로 붙인 게 아니라 실제 검증 대상이므로 정직함)

## 2. 서비스 정의

### 2.1 입력 (사용자가 주는 것)

| # | 입력 | 형식 | 사용자 부담 |
|---|---|---|---|
| 1 | 회로도 토폴로지 | **IPC-D-356 넷리스트** (Flux·KiCad·Altium 공통 export) | Export 1회 |
| 2 | **부품 식별 (필수)** | **BOM CSV** — refdes → MPN | Export 1회 |
| 3 | 펌웨어 | 소스 디렉토리 (`.ino`, `.cpp`, `.h`) 또는 GitHub URL | 없음 |
| 4 | 부품 데이터시트 | **자동 수집** — BOM의 MPN으로 검색·다운로드 | 없음 |

### ✅ D1 실측 결과 (2026.08.16, 팀원의 실제 보드로 검증)

`esp32c6presencesmartlight.d356` (Flux export)를 파싱한 결과:

- **성공** — 네트 8개, 부품 10개, 연결관계 전부 추출. `parse_d356.py`
- **성공** — K1처럼 6개 패드가 전부 `pad-`로 이름이 같은 부품도 **X좌표 클러스터링으로 제어부/스위치부 분리** 성공. 이름이 잃은 걸 기하가 되찾음
- **한계 1** — 핀 이름이 **4글자로 잘림** (`LP-G`, `SDIO`, `D10_`, `D9_M`). **정확한 GPIO 번호를 알 수 없음**
- **한계 2** — **MPN·부품값·제조사 정보가 전혀 없음**

> ### 🔴 이 발견이 제품 정의를 바꿉니다
> **BOM export는 선택 기능이 아니라 제품의 절반입니다.**
> MPN이 없으면 "K1이 옵토커플러형인지 트랜지스터형인지" 모르고,
> 모르면 무조건 플래그를 세웁니다. **→ 오탐 생성기가 됩니다.**
> 그리고 모듈 핀 이름(`D7`, `D8`, `LP-GPIO`)을 GPIO 번호로 바꾸려면
> **모듈 핀아웃 DB**가 따로 필요합니다 (XIAO ESP32C6 등).

> 넷리스트를 쓰는 이유: `.kicad_sch` 원본보다 파싱이 압도적으로 쉽고, **부품–핀–네트 관계가 명시적**입니다. 사용자 부담도 클릭 한 번입니다.

### ⚠️ Flux 사용 관련 결정 (2026.08.16)

**팀원이 Flux를 쓰더라도, 데모 보드는 KiCad로 그립니다.** 이유 두 가지:

1. **기술적** — Flux는 브라우저 기반이고 **공식 넷리스트 export가 확인되지 않습니다.** 검색에 나오는 KiCad export는 사용자가 만든 [샌드박스 프로젝트](https://www.flux.ai/natarius/kicad-export-sandbox)지 공식 기능이 아닙니다. 공개 API도 없습니다. **입력이 없으면 파이프라인이 성립하지 않습니다.**
2. **전략적** — 경쟁자 플랫폼 위에서 데모하는 그림이 됩니다. 심사위원이 Flux를 알면 첫 질문이 "그거 Flux가 하는 거 아닌가요"가 됩니다.

검증 데이터셋으로 쓸 GitHub 오픈소스 레포도 대부분 KiCad입니다.
→ **팀원은 본인 작업에 Flux를 계속 쓰되, Rev A/Rev B 데모 보드만 KiCad로 그릴 것.**

### 2.2 처리 파이프라인 (에이전트 7단계)

```
[1] 넷리스트 파싱          → 부품/핀/네트 그래프          [결정적 코드]
[2] MCU 식별 + 핀 매핑     → "GPIO34 ↔ NET_LED1"          [결정적 코드]
[3] 펌웨어 정적 분석       → 코드가 쓰는 핀 번호 + 모드    [코드 + LLM]
[4] 외부 부품 MPN 추출     → 데이터시트 검색·다운로드      [에이전트: 웹 도구]
[5] 데이터시트 사실 추출   → Voh/Vol/최대정격/필요풀업     [LLM]
[6] 규칙 엔진 실행         → 위 사실들로 결정적 판정       [결정적 코드]
[7] 리포트 생성            → 근거 위치 포함               [코드 + LLM]
```

이 7단계가 "질문에 답하는 게 아니라 실제 업무를 수행한다"의 증거입니다.

### 2.3 설계 원칙 — 이게 우리 팀의 무기

> **LLM은 읽기만 한다. 판정은 코드가 한다.**

- LLM 출력은 반드시 **구조화된 사실(JSON)**로만 받습니다.
  ```json
  { "part": "U2", "pin": "OUT", "vout_max": 5.0,
    "source": "MAX6675 datasheet p.3 Table 2" }
  ```
- 판정은 그 사실들에 대한 **순수 함수**입니다. `if vout_max > mcu.vih_max: FAIL`
- 이유 세 가지:
  1. **재현 가능** — 같은 입력이면 항상 같은 결과. LLM처럼 답이 흔들리지 않음
  2. **근거 추적 가능** — 모든 판정에 "데이터시트 몇 페이지 몇 번 표" 링크
  3. **오탐 수정 가능** — 규칙 단위로 고침. 프롬프트를 주무르지 않음

**발표에서 이걸 강조합니다.** "그냥 GPT 래퍼 아니냐"를 정면으로 막는 유일한 방법이고, 우리가 이미 해본 구조입니다.

> ⚠️ **주의**: Flux도 자사 Design Review를 "combines deterministic algorithms with AI"라고 설명합니다.
> 이 아키텍처는 **우리만의 차별점이 아닙니다.** *올바름*의 근거로만 쓰고, *차별성*의 근거로는 쓰지 마세요.
> 차별성은 오직 하나 — **기존 코드와 현재 회로도의 드리프트를 보는 것**입니다.

### 2.4 출력물

HTML 리포트. 항목마다 반드시 세 가지 근거를 답니다.

```
[치명] GPIO34에 출력 설정 — 입력 전용 핀
  회로도  : D1 (LED) ↔ NET_LED1 ↔ U1.GPIO34
  코드    : src/main.cpp:42  pinMode(LED_PIN, OUTPUT)   // LED_PIN = 34 (config.h:8)
  근거    : ESP32 datasheet §4.1.1 — GPIO34-39 are input-only
  수정 제안: GPIO 4, 5, 16, 17 중 하나로 변경 (현재 미사용 확인됨)
```

## 3. 판정 규칙 카탈로그

발표까지 목표 8~10개. **R4·R6이 아이템의 존재 이유입니다** — 표 조회로 절대 안 되고 데이터시트를 실제로 읽어야 합니다.

| # | 규칙 | 심각도 | 필요한 것 |
|---|---|---|---|
| R1 | 코드가 GPIO 34~39에 `OUTPUT`/풀업 설정 | 치명 | 룩업 |
| R2 | 회로도가 GPIO 6~11에 연결 (SPI flash 전용) | 치명 | 넷리스트 |
| R3 | strapping 핀(GPIO 0/2/12/15) 부팅 상태 오류 | 치명 | 넷리스트 |
| **R4** | **외부 부품 출력 전압이 GPIO 입력 최대 초과** | **치명** | **★데이터시트** |
| R5 | ADC2 채널 사용 + 같은 빌드에 WiFi 초기화 | 경고 | 코드 흐름 추적 |
| ~~R6~~ | ~~I2C 풀업 저항 누락~~ | — | **폐기 — Flux Design Review가 이미 함** |
| **R7** | **코드가 쓰는 핀이 회로도에 미연결** | 치명 | 교차 |
| **R8** | **회로도에 연결된 핀을 코드가 초기화 안 함** | 경고 | 교차 |
| **R10** | **회로도가 바뀐 뒤 코드가 안 따라옴 (드리프트)** | 치명 | 교차 + git 이력 |
| R9 | 부팅 시 출력이 나오는 핀(GPIO1 TX 등)에 부하 | 정보 | 넷리스트 |
| **R11** | **네트 이름이 주장하는 전압 ≠ 소스 부품의 전원 도메인** | 경고 | **넷리스트만** |
| **R12** | **높은 전원 도메인 부품이 낮은 도메인을 직결 (직렬소자 없음)** | 치명 | **넷리스트만** |

### ★ R11·R12 — 2026.08.16 팀원 보드에서 실측 발견

**데이터시트 조회 0회로 뜨는 규칙입니다.** 이게 아키텍처를 증명합니다.

> **토폴로지가 질문을 던지고, 데이터시트가 답한다.**
> 결정적 코드가 플래그를 세우고, LLM은 그걸 **지우기 위해서만** 호출된다.

실제 검출 결과 (`check.py`):

| 발견 | 검증 결과 |
|---|---|
| R11 `PRESENCE_3V3` | **유효, 미해결.** 네트 이름은 3.3V인데 소스 U2는 `5V_BUS`. LD2410 계열로 보이나 유명 튜토리얼 페이지들도 OUT 로직 레벨을 안 적어둠 — **데이터시트를 열어야만 판정 가능** |
| R12 `PRESENCE_3V3` | **중복 발생.** 같은 네트에 두 규칙이 겹침 → **엔진 버그, dedup 필요** |
| R12 `_IN_ACTIVE_LOW` | **오탐 유력.** 옵토형 릴레이 모듈은 IN에 5V 풀업이 없고 2.2kΩ 직렬 LED (약 0.95mA). 5V 역류 없음 |

**3건 중 유효 1건, 중복 1건, 오탐 1건.**
오탐 문제가 D6–7이 아니라 **D1에 드러난 것이 이 프로젝트 최대의 행운**입니다.
지금부터 오탐 억제가 최우선 과제입니다.

> **R7·R8·R10이 이 제품의 존재 이유입니다.** 다른 어떤 도구도 구조적으로 못 잡습니다.
> R6은 Flux가 "Pull-Up/Pull-Down Configuration" 검사로 이미 제공하므로 폐기했습니다.
> R4도 Flux가 "Capacitor Voltage Margins"로 인접 영역을 건드리고 있으니, 발표에서는
> **"GPIO 입력 정격 초과"라는 우리 각도를 명확히 구분**해서 말할 것.

## 4. 안 만드는 것 (범위 제외)

발표에서 이 목록을 보여주면 신뢰가 올라갑니다. 범위를 아는 팀으로 보입니다.

- Altium / OrCAD / PDF 회로도 → **안 함** (KiCad 넷리스트만)
- ESP32 외 MCU → **안 함** (구조는 확장 가능하게, 구현은 ESP32만)
- PCB 레이아웃 DRC → **안 함** (JLCPCB·PCBWay·NextPCB가 발주 시 무료, KiCad 내장)
- 회로 자동 설계·배치 → **안 함** (Quilter, DeepPCB, Flux 영역)
- 아날로그 시뮬레이션 → **안 함**

### PCB 레이아웃을 뺀 진짜 이유

무료라서만이 아닙니다. **레이아웃에는 펌웨어와의 교차점이 거의 없습니다.**
넷리스트가 같으면 레이아웃이 어떻든 코드는 똑같습니다.
레이아웃으로 확장하는 순간 우리가 유일하게 가진 축(코드 ↔ 회로도)이 사라지고, **그냥 약한 EDA 툴**이 됩니다.

**예외 하나 — 확장 슬라이드용**
ESP32 **안테나 keepout**은 레이아웃 항목이지만, *문제인지 아닌지가 코드에 달려 있습니다.*
안테나 아래 구리가 있어도 WiFi를 안 쓰면 상관없고, 쓰면 치명적입니다.
레이아웃만 봐도 모르고 코드만 봐도 모릅니다. **우리 구조에서만 판정되는 항목**이라
"이 방향으로 확장하면 이런 게 나옵니다"의 예시로 정확합니다. **지금 만들지는 않습니다.**

## 5. 검증 계획 (숫자를 만든다)

외부 기관 컨택 0. 전부 공개 데이터와 자체 제작으로 합니다.

### 데이터셋 A — 오픈소스 레포 (재현율 측정)

1. GitHub에서 **KiCad 파일 + ESP32 펌웨어가 같은 레포**에 있는 프로젝트 수집. 목표 30~50개
2. 커밋 히스토리에서 핀 관련 수정 커밋 검색:
   `fix pin`, `wrong pin`, `wrong gpio`, `pinout fix`, `hardware bug`, `rev b`
3. **수정 직전 커밋 상태 = 실제 발생했던 버그 = 정답 라벨**
4. 그 시점 파일을 Prefab에 넣어 검출 여부 측정
5. 보조공학 하드웨어 레포(`makersmakingchange`, `openassistive`, GitHub `disability`/`openat` 토픽)를 반드시 섞을 것 → 사회기여 서사

### 데이터셋 B — 자체 결함 주입 (오탐율 측정)

정상 보드 1개를 설계하고 규칙별로 결함을 심습니다. 규칙당 3케이스 = 약 30케이스.
정상 케이스도 같은 수만큼 넣어 **오탐율**을 잽니다.

### 발표에 올릴 문장

## 7-A. "시장이 좁지 않나요" 대응 — 팀장 최대 관심사

### 먼저: 심사기준에 "시장 크기"도 "공감도"도 없습니다

2번 항목은 *"실제 사용자의 불편함을 **정확히 타당하게** 짚어냈는가"*입니다.
**넓게 흐린 것보다 좁게 정확한 쪽이 점수가 높은 구조입니다.**

### 공감은 시장 크기가 아니라 연출의 문제

심사위원은 PCB를 설계해본 적이 없습니다. 그러나 이건 100% 겪었습니다 —
*분명히 맞게 했는데 안 되는 경험 / 하루 종일 찾았더니 한 줄이었던 경험 / 물어볼 사람이 없던 경험.*

**공감의 축을 "하드웨어"에서 "혼자 헤매는 시간"으로 옮깁니다.**

| ❌ 하지 말 것 | ✅ 할 것 |
|---|---|
| "임베디드 핀맵 불일치 검증 도구입니다" | "분명히 맞게 했는데 안 켜집니다. 컴파일도 되고 업로드도 되고 에러도 없습니다. 찾는 데 반나절 걸립니다." |

**LED가 안 켜지는 건 다섯 살도 압니다.** 실물로 시작하면 설명이 필요 없습니다.

### 심사위원 본인의 경험으로 연결하는 한 문장

> "여기 계신 분 중에, **학생 캡스톤 보드가 안 켜져서 밤새우는 조교**를 본 적 있으신 분이 계실 겁니다."

우리 2순위 고객이 대학 임베디드 수업입니다. 심사위원이 직접 목격한 장면입니다.

### "좁다"를 심사위원보다 먼저 말할 것

질문받고 방어하면 지고, 먼저 말하면 판단력으로 읽힙니다.

> "네, 좁습니다. **저희가 알고 골랐습니다.**
> 넓은 문제는 이미 정부와 대형 플랫폼이 다 풀어놨습니다.
> 후보 20개를 검색으로 검증했고 **19개가 이미 존재하거나 무료였습니다.** 남은 하나를 골랐습니다."

→ **폐기한 20개 후보 표를 슬라이드 한 장에 그대로 올릴 것.**
2번 항목 *"사전조사가 충분한가"*의 만점 재료이고, 좁은 선택이 무지가 아니라 **판단**이었다는 증거입니다.

### 규모는 가로가 아니라 세로로

- ❌ "사용자가 10만 명입니다" — 우리가 못 하는 말
- ✅ **"한 번 놓치면 2주와 수백만 원입니다"** — 출처 있는 숫자로 할 수 있는 말

### 남는 위험 (인정하고 대비)

캠퍼스체크는 5초 만에 이해되고 **우리는 20초가 필요합니다.** 사실입니다.
대응은 하나뿐 — **첫 20초 안에 LED가 안 켜지는 걸 보여주는 것.**
슬라이드로 시작하면 지고 물건으로 시작하면 이깁니다. **이 20초만 리허설에서 열 번 연습할 것.**

## 8. 심사위원 예상 질문

**Q. ChatGPT한테 물어보면 되는 거 아닌가요?**
넷리스트 수백 줄 + 코드 수십 파일 + 데이터시트 수백 페이지를 한 번에 넣을 수 없습니다. 그리고 GPT는 같은 질문에 매번 다르게 답합니다. 우리는 LLM에게 **읽기만** 시키고 판정은 코드가 결정적으로 합니다. 같은 입력이면 항상 같은 결과입니다.

**Q. esp32pin.com 같은 게 이미 있잖아요?**
그건 **표**입니다. 사용자의 파일을 읽지 않습니다. 우리는 당신의 회로도와 당신의 코드를 대조합니다.

**Q. Traceformer, AllSpice DRCY가 있는데요?**
회로도만 봅니다. 펌웨어를 안 읽습니다. **실제 사고는 둘 사이에서 납니다.**

**Q. Flux Copilot이 이미 핀 매핑을 해주지 않나요?** ← **가장 중요한 질문. 반드시 준비할 것**
Flux는 **회로도에서 코드를 만들어 주는** 방향입니다. 한 방향, 한 번입니다.
문제는 그다음입니다. **회로도를 고치고 코드를 안 고쳤을 때 Flux는 아무 말도 하지 않습니다.**
오히려 Flux로 초기 코드를 생성한 팀일수록 더 위험합니다. 처음 한 번은 자동으로 맞았으니 그 뒤로 안 보거든요.
우리는 그 어긋남을 **PR마다** 잡습니다.

**Q. Flux Design Review가 데이터시트도 읽던데요?**
읽습니다. 그리고 저항 정격, 커패시터 전압, 풀업/풀다운을 검사합니다. **전부 회로도 안에서 끝나는 검사입니다.**
저희가 보는 건 회로도 *바깥* — 사용자가 써놓은 코드입니다. 저희는 R6(풀업)을 **의도적으로 뺐습니다.** Flux가 이미 하니까요.

**Q. 오탐이 나면 어떻게 하나요?**
오탐율을 함께 공개합니다. 그리고 판정이 결정적이라 오탐 원인을 규칙 단위로 추적해서 고칠 수 있습니다. 프롬프트를 주무르는 방식으로는 불가능한 일입니다.

**Q. 시장이 좁지 않나요?**
좁습니다. 정확한 규모는 **추가 조사가 필요합니다.** 다만 진입 지점으로는 ESP32 단일 생태계만으로 충분하고, 규칙 엔진 구조는 MCU 교체로 확장됩니다.

**Q. 왜 학생팀이 이걸 하나요?**
우리가 그 문제를 직접 겪습니다. **우리 팀이 첫 사용자입니다.**

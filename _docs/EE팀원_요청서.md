## A. 지금 당장 받아야 할 것 (파일)

### 🔴 A-1. 펌웨어 소스코드 — **최우선**

`esp32c6presencesmartlight` 프로젝트의 **코드 전체**. GitHub 링크든 zip이든 상관없습니다.

**왜 1순위인가**: 지금 회로도만 있어서 규칙 절반이 못 돕니다.
우리 제품의 핵심(코드가 쓰는 핀 ↔ 회로도가 연결한 핀 대조)은 **코드가 없으면 아예 실행이 안 됩니다.**
회로도만으로 도는 규칙 2개(R11·R12)는 이미 돌렸고 3건 잡았습니다. 나머지는 코드 대기 중입니다.

> 요청 문구: "그 보드 펌웨어 코드 좀 줘. `.ino`나 `.c`/`.h` 파일 전부. 깃허브면 링크만."

### 🔴 A-2. BOM (부품 목록) CSV — **최우선**

Flux에서 BOM export. 필요한 열:

| 열 | 예시 | 필수 |
|---|---|---|
| Reference | U2 | ✅ |
| **MPN (제조사 부품번호)** | HLK-LD2410C | ✅ **이게 핵심** |
| Manufacturer | Hi-Link | ✅ |
| Value | 5.1k | 권장 |
| Footprint | 0402 | 선택 |

**왜 필수인가**: 우리가 받은 IPC-D-356 파일에는 **부품 번호가 하나도 없습니다.**
그래서 도구가 "K1이 어떤 릴레이인지" 모르고, 모르면 무조건 경고를 띄웁니다.
실제로 오늘 오탐이 1건 나왔습니다. **MPN이 없으면 우리 제품은 오탐 생성기입니다.**

> 요청 문구: "Flux에서 BOM CSV로 뽑아줘. 부품번호(MPN) 열이 꼭 있어야 해."

### 🟡 A-3. 부품 3개의 정확한 모델명

파일에서 이름이 4글자로 잘려서 추정만 했습니다. **확인해 주세요.**

| 기호 | 우리 추정 | 확인 필요한 것 |
|---|---|---|
| **U1** | Seeed XIAO ESP32C6 | 맞나? (핀 이름이 `D7_R`, `D8_S`, `D9_M`, `D10_`, `LP-G`로 잘려 있음) |
| **U2** | HLK-LD2410 계열 인체감지 센서 | 맞나? **OUT 핀이 3.3V인지 5V인지** |
| **K1** | 5V 릴레이 모듈 | **옵토커플러형인가, 트랜지스터형인가** |

K1이 특히 중요합니다. 옵토형이면 오늘 뜬 경고 1건은 오탐이고, 트랜지스터형이면 진짜 문제입니다.
**이 답 하나로 우리 도구의 정확도 판정이 갈립니다.**

### 🟡 A-4. 과거 프로젝트 2~3개 더

같은 형식(IPC-D-356 + BOM + 펌웨어) 세트로. **회로도와 코드가 짝으로 있는 것**만.
검증 샘플이 1개면 "우연히 됐다"가 되고, 3~4개면 "된다"가 됩니다.

### 🟢 A-5. 회로도 PDF

사람이 눈으로 대조할 때 필요합니다. 도구 입력용은 아닙니다.

## B. 사야 할 하드웨어 (데모용)

**PCB는 발주하지 않습니다.** 배송에 5~7일 걸려서 재시도 여유가 없습니다.
브레드보드로 충분하고, 오히려 **점퍼선 옮겨 꽂는 게 관객 눈에 보여서 더 낫습니다.**

| 품목 | 수량 | 용도 | 비고 |
|---|---|---|---|
| ESP32 DevKit | 1 | 데모 본체 | **팀원 보유 — 확인만** |
| 브레드보드 (830핀) | 1 | 회로 구성 | |
| 점퍼선 수-수 | 1세트 | 배선 | |
| LED 5mm | 5 | 켜짐/안 켜짐 시연 | 색 아무거나 |
| 저항 330Ω | 5 | LED 전류 제한 | 220~1k 아무거나 |
| USB 케이블 | 1 | DevKit 연결 | **커넥터 종류 확인 필요** |
| **작년 프로젝트 실물 보드** | 1 | 오프닝 소품 | **있으면 최고. 반드시 물어볼 것** |
| 멀티미터 | 1 | 전압 실측 시연 | 있으면 좋음, 없어도 됨 |

전부 흔한 부품이라 **팀원이 이미 갖고 있을 확률이 높습니다. 사기 전에 먼저 물어보세요.**
없으면 디바이스마트·엘레파츠 온라인 주문.

> ⚠️ **시연 중에 진짜로 5V를 ESP32에 물리지 마세요.** 정말로 망가집니다.
> 과전압은 "도구가 경고를 띄우는 화면"으로만 보여줍니다.

## C. EE 팀원에게 물어볼 질문 8개

**이 답변들이 그대로 제품의 판정 규칙이 됩니다.** 녹음하거나 받아 적으세요.
비전공자가 물어봐도 되는 질문들로 골랐습니다.

1. **"보드 만들었는데 처음에 안 켜졌던 적 있어? 그때 원인이 뭐였어?"**
   → 가장 중요한 질문. 실제 겪은 실패가 규칙 1개입니다.

2. **"회로도 검토할 때 제일 먼저 뭘 봐?"**
   → 검토 순서가 곧 규칙의 우선순위입니다.

3. **"데이터시트에서 '이 핀에 몇 볼트까지 넣어도 되는지'는 어느 표를 봐?"**
   → 이 답이 있어야 AI에게 "어디서 뭘 찾아라"를 시킬 수 있습니다.

4. **"5V로 돌아가는 부품 출력을 3.3V 칩에 바로 연결해도 되는 경우가 있어? 어떤 때 괜찮고 어떤 때 안 돼?"**
   → 오늘 뜬 경고 2건이 정확히 이 케이스입니다.

5. **"릴레이 모듈 IN 핀에 3.3V 넣어도 돼? 안 되는 모듈도 있어?"**
   → 오탐 판정에 직결됩니다.

6. **"쓰면 안 되는 핀 같은 게 있어? 왜 안 돼?"**
   → 입력 전용 핀, 부팅 관련 핀 등이 여기서 나옵니다.

7. **"회로 고치고 코드 안 고쳐서 고생한 적 있어?"**
   → 우리 제품의 핵심 서사입니다. 실제 사례가 있으면 발표에 그대로 씁니다.

8. **"혼자 하면서 '이거 물어볼 사람 있었으면' 했던 순간 있어?"**
   → 사회문제 슬라이드의 인용문이 됩니다.

## D. 두 사람의 역할 (합의해 둘 것)

"개발 안 하는 사람"이 아닙니다. **제품 정확도의 책임자**입니다.
공모전 배점 중 **융합 구성·협업 20점이 여기서 나옵니다.**

| 역할 | 내용 |
|---|---|
| **규칙 정의** | 무엇이 위험인지 정하고, 데이터시트 어느 표의 어느 값을 봐야 하는지 명시 |
| **오탐 검수** | 도구가 띄운 경고가 진짜인지 판정. **이게 지속 업무이고 가장 중요합니다** |
| **정답 라벨링** | GitHub 오픈소스 프로젝트의 커밋이 진짜 핀 버그 수정인지 판별 |
| **데모 하드웨어** | Rev A / Rev B 배선 구성, 리허설 시 실물 담당 |

발표에서 이렇게 말할 수 있어야 합니다:
> "이 규칙들은 저희 팀 하드웨어 담당이 실제로 보드를 태워먹으면서 만든 목록입니다."

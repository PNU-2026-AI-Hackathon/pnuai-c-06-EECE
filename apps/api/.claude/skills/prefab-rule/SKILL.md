# Prefab 판정 규칙 작성

이 스킬은 **회로를 아는 사람이 코딩을 몰라도 규칙을 기여할 수 있게** 만드는 것이 목적이다.
사용자가 자연어로 "이런 상황이 위험하다"고 말하면, 아래 절차대로 규칙을 완성한다.

## 절차

### 1단계 — 되묻는다 (건너뛰지 말 것)

규칙을 쓰기 전에 반드시 네 가지를 확정한다. 사용자가 비전공자일 수 있으니 **쉬운 말로** 묻는다.

1. **무엇이 잘못된 상황인가** — 한 문장으로
2. **무엇을 봐야 아는가** — 회로도만? 코드도? 데이터시트도?
3. **얼마나 나쁜가** — 보드가 망가짐(치명) / 오동작(경고) / 알아두면 좋음(정보)
4. **괜찮은 경우도 있는가** — 예외가 있으면 그게 오탐의 원인이 된다

예시 대화:
> 사용자: "5V 부품을 3.3V 핀에 바로 물리면 안 돼"
> → "회로도만 보고 알 수 있나요, 아니면 그 부품 데이터시트를 봐야 하나요?"
> → "출력이 3.3V 레벨인 5V 부품도 있나요?" (있다면 → UNRESOLVED 처리 필요)

### 2단계 — 등급을 판정한다

`CLAUDE.md` 3절 기준으로 **기본 / 차별**을 매긴다.

- **회로도만으로 판정되면 → 기본.** Traceformer가 이미 한다. 만들어도 되지만 발표 중심에 두지 않는다.
- **펌웨어 코드를 읽어야 하면 → 차별.** 우선순위 최상.

등급을 사용자에게 명시적으로 알린다:
> "이건 회로도만으로 되는 규칙이라 **기본** 등급입니다. Traceformer가 이미 하는 범위예요.
> 만들긴 하되, 발표에서는 R7·R8 같은 차별 규칙을 앞세우는 게 좋습니다."

### 3단계 — 필요한 사실(fact)을 정의한다

판정 함수는 **네트워크도 LLM도 호출하지 않는다.** 필요한 모든 정보는 fact로 미리 받는다.

```python
# 사실은 이런 모양이다. 반드시 출처가 붙는다.
{"part": "U2", "field": "voh_max", "value": 5.0, "unit": "V",
 "source": "HLK-LD2410C datasheet p.3 Table 2"}
```

데이터시트가 필요한데 fact가 없으면 → **UNRESOLVED**를 반환한다. 추측 금지.

### 4단계 — 규칙 함수를 쓴다

`rules/` 아래 `r{번호}_{짧은이름}.py` 로 만든다. 아래 형태를 그대로 따른다.

```python
"""R07 — 코드가 쓰는 핀이 회로도에 연결되어 있지 않다."""
from prefab.types import Finding, Severity, Verdict, Evidence

RULE_ID    = "R07"
TITLE      = "코드가 쓰는 핀이 회로도에 미연결"
SEVERITY   = Severity.CRITICAL
TIER       = "차별"          # 기본 | 차별
NEEDS      = ["netlist", "firmware"]   # netlist | firmware | datasheet | git


def check(ctx) -> list[Finding]:
    """순수 함수. ctx만 읽고 Finding 리스트를 반환한다.

    금지: 네트워크 호출, LLM 호출, 파일 읽기, 시간·난수 사용.
    """
    out = []
    for use in ctx.firmware.pin_uses:               # 코드가 실제로 쓰는 핀
        net = ctx.netlist.net_of_mcu_pin(use.pin)   # 회로도가 그 핀에 물린 네트
        if net is not None:
            continue
        out.append(Finding(
            rule=RULE_ID,
            severity=SEVERITY,
            verdict=Verdict.FAIL,
            net=None,
            claim=f"코드는 {use.pin}을 {use.mode}로 쓰는데, 회로도에서 이 핀은 어디에도 연결되어 있지 않습니다.",
            evidence=[
                Evidence.firmware(use.file, use.line, use.snippet),
                Evidence.netlist(f"{ctx.netlist.mcu}.{use.pin} → (미연결)"),
            ],
            suggestion=f"{use.pin} 배선을 추가하거나, 코드에서 이 핀 사용을 제거하세요.",
        ))
    return out
```

**규칙 작성 시 반드시 지킬 것**

- `check()`는 순수 함수. 부작용 없음.
- 임계값은 이름 있는 상수로. 매직넘버 금지.
- `claim`은 **비전공자가 읽어도 이해되는 한국어 한 문장**. 전문용어 최소화.
- `evidence`는 최소 2개. 회로도 근거 + 코드 근거(또는 데이터시트 근거).
- 필요한 fact가 없으면 `Verdict.UNRESOLVED`와 **무엇이 있어야 판정 가능한지**를 담는다.

### 5단계 — 테스트 3개를 반드시 쓴다

`tests/test_r{번호}.py`. 세 개 미만이면 미완성이다.

```python
def test_r07_detects():        # 양성 — 진짜 문제를 잡는가
def test_r07_no_false_alarm(): # 음성 — 정상 회로에서 조용한가
def test_r07_unresolved():     # 미해결 — 정보 부족 시 추측하지 않는가
```

가능하면 **팀원의 실제 보드(`fixtures/esp32c6presencesmartlight.d356`)**를 음성 테스트에 쓴다.
실제 보드에서 새 경고가 뜨면 그건 발견이거나 오탐이다. 둘 중 무엇인지 사용자에게 확인한다.

### 6단계 — 등록하고 보고한다

`rules/__init__.py`의 레지스트리에 추가하고, `CLAUDE.md` 7절 표의 상태를 갱신한다.

작업을 마치면 이 형식으로 보고한다:

```
R07 추가 완료 — 등급: 차별
  잡는 것 : 코드가 쓰는 핀이 회로도에 미연결
  필요한 것: 넷리스트 + 펌웨어
  테스트  : 3/3 통과
  실제 보드: 신규 경고 0건 (오탐 없음)
```

## 오탐 수정 요청을 받았을 때

"이거 잘못 떴어"는 가장 중요한 피드백이다. 순서대로 처리한다.

1. **왜 떴는지** 그 케이스의 fact를 그대로 보여준다
2. 진짜 오탐인지, 아니면 fact가 틀린 건지 구분한다
   - 규칙이 틀림 → 조건을 좁힌다
   - fact가 틀림 → 데이터시트 추출을 고친다 (규칙은 건드리지 않는다)
   - 부품 식별 실패 → `UNRESOLVED`로 강등한다. **조용히 통과시키지 않는다.**
3. 그 케이스를 **음성 테스트로 고정**한다. 다시는 재발하지 않게.

## 하지 말 것

- 규칙 함수 안에서 LLM에게 판단을 묻는 것
- 부품을 모르는데 안전하다고 가정하는 것
- 테스트 없이 규칙만 추가하는 것
- 회로도만으로 되는 규칙을 "차별" 등급이라고 말하는 것

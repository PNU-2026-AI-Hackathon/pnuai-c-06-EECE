# Prefab API — 프로젝트 헌법

이 저장소에서 작업하는 모든 세션은 이 파일을 먼저 읽는다.
여기 적힌 것과 충돌하는 제안은 하지 않는다.

**저장소 역할**: 파서 · 규칙 엔진 · REST API. 화면은 `prefab-web`이 담당한다.
**마감**: 2026-08-28 최종 발표. 그 전에 접속 가능한 URL이 있어야 한다.

---

## 1. 이 제품이 하는 일

> **이미 짜놓은 펌웨어가 바뀐 회로도를 따라가고 있는지 검사한다.**
> 회로도 · 펌웨어 · 부품 데이터시트를 함께 읽고, 셋 사이의 어긋남을 보드 발주 전에 잡는다.

한 방향·한 번이 아니라 **양방향·계속**이다. 최종 형태는 PR마다 도는 CI 검사다.

---

## 2. 절대 불변 원칙

### 2-1. LLM은 읽기만 한다. 판정은 코드가 한다.

```
토폴로지가 질문을 던지고, 데이터시트가 답한다.
→ 결정적 코드가 플래그를 세운다 (LLM 없이)
→ LLM은 그 플래그를 "지우기 위해서만" 호출된다
```

- LLM 출력은 **반드시 JSON 스키마로 강제**한다. 자유 텍스트 판정 금지.
- `check()` 판정 함수는 **순수 함수**다. 네트워크·LLM·파일 IO·시간·난수 사용 금지.
- 모든 판정에는 **근거 위치**가 붙는다 (파일:라인 / 데이터시트 페이지·표).

같은 입력에 다른 결과가 나오는 순간 제품이 죽는다. 이 원칙을 어기는 코드는 머지하지 않는다.

### 2-2. 모르면 모른다고 한다

부품을 식별하지 못하면 `UNRESOLVED`를 반환한다. 추측해서 `PASS`나 `FAIL`을 내지 않는다.
데이터시트에서 값을 못 찾으면 `null`과 이유를 남긴다. **지어내지 않는다.**

### 2-3. 오탐이 최우선 적이다

린터는 오탐률이 높으면 3일 만에 꺼진다. 규칙을 늘리는 것보다 오탐을 줄이는 것이 항상 우선.

### 2-4. 못 한 일을 숨기지 않는다

BOM이 없어서 규칙 5개를 못 돌렸으면 응답에 `skipped`로 그대로 실린다.
규칙을 못 돌렸는데 "이상 없음"처럼 보이는 응답은 만들지 않는다.

## 3. 경쟁 경계 — 무엇을 만들고 무엇을 만들지 않는가

| 기능 | 누가 이미 함 | 우리 등급 |
|---|---|---|
| 회로도 단독 검사 (전압 도메인, 풀업, boot mode, floating pin) | **Traceformer $20/월**, Flux Design Review | **기본** |
| 데이터시트 기반 검증 | Traceformer | **기본** |
| 회로도 → 펌웨어 코드 생성 | Flux Copilot, Embedder | **안 만든다** |
| 코드 생성 후 실물 보드 플래시·테스트 | Embedder (보드 필요) | **안 만든다** |
| **기존 펌웨어 ↔ 현재 회로도 대조** | **없음 (확인됨)** | **차별 — 자원을 여기 몰아넣는다** |

> Traceformer 공식 문서: *"no mention of firmware, code analysis, or software validation"*

**새 규칙을 제안할 때는 반드시 등급을 먼저 판정한다. 회로도만으로 되는 규칙은 "기본"이다.**

## 4. 범위 밖 — 제안하지 말 것

- PCB 레이아웃 DRC / DFM — JLCPCB·PCBWay가 발주 시 무료
- 자동 배치·배선 — Quilter, DeepPCB 영역
- 아날로그 시뮬레이션
- ESP32 외 MCU — 구조는 확장 가능하게, **구현은 ESP32만**
- 인증 · 회원가입 · 결제 — 8/28까지 만들지 않는다
- Postgres · Redis · Celery · 마이크로서비스
- 계약(`API_CONTRACT.md`)에 없는 응답 필드

## 5. IPC-D-356 — 하드윈 지식

고정폭 오프셋 (0-indexed, 실측 검증됨):

```
[0:3]    레코드 타입   317=through-hole/via, 327=SMT
[3:17]   네트명 (14자)
[20:26]  reference designator (6자)
[26]     '-' 구분자
[27:31]  핀 이름 (4자)   ← 4글자로 잘린다
[32:37]  드릴 'D'+4
[37]     도금 P/U
[38:41]  access 'A00'~'A03'
[41:49]  X 'X'+부호+6자리 (0.0001 inch)
[49:57]  Y 'Y'+부호+6자리
```

### 이 형식의 한계 (반드시 기억)

1. **핀 이름이 4자로 절단된다.** `LP-G`, `SDIO`, `D10_`, `D9_M`
   → **정확한 GPIO 번호를 알 수 없다.** 모듈 핀아웃 DB가 별도로 필요하다.
2. **MPN·부품값·제조사가 전혀 없다.** → BOM CSV가 있어야 부품을 짚는다.
3. 다중 패드 부품은 핀 이름이 전부 같을 수 있다 (K1의 6개 패드가 모두 `pad-`).
   → **X좌표 클러스터링으로 물리 그룹을 복원한다.** 구현·동작 확인됨.

### 그래서 회로도 넷리스트도 읽는다 (8/19)

**위 한계는 IPC-D-356 의 것이지 우리 문제의 성질이 아니다.** 이 형식은 제조용이라
사람이 읽는 이름을 안 싣는다. 그걸 모르고 한동안 BOM 이 유일한 길이라고 적어 뒀다.

실제 KiCad 보드 3개에서 R07·R08 이 통째로 침묵했고, 통제 실험으로 원인을 확정했다 —
**우리 보드의 핀 이름만 번호로 바꾸니 pinmap 이 11 → 0, 발견이 5 → 2건이 됐다.**
BOM 은 양쪽 arm 에 다 넣었는데도 그랬다. 우리 보드가 되던 것은 **Flux 가 IPC-D-356 에
실크 이름을 실어 주기 때문**이고, 한 도구에서만 되는 걸 모르고 지나갔다.

```
kicad-cli sch export netlist --format kicadxml -o board.xml board.kicad_sch
```

| 같은 보드에서 얻는 것 | IPC-D-356 | kicadxml |
|---|---|---|
| 부품번호 (LCSC·MPN) | 0% | **100%** (52/52) |
| 데이터시트 URL | 0% | **100%** |
| 핀 이름 | **0%** | **62%** (115/183) |

- 형식은 **확장자가 아니라 내용으로** 가른다 (`netlist/detect.py`). 사용자는 파일 이름을 바꾼다
- 둘 다 `Netlist` 로 나온다. **규칙은 어느 형식인지 모른다**
- 회로도 넷리스트에는 **좌표가 없다.** 기하 기반 실크 복원과 좌표 클러스터링이 안 돈다.
  대신 핀 이름이 직접 오므로 그 복원이 필요 없다. 못 하는 것은 파이프라인에 그대로 실린다
- **형식마다 다른 성질은 `Netlist.NAME_IS_WIDTH_LIMITED` 로 가른다.** 회로도 넷리스트는
  이름을 안 자르므로 14자 절단 경고를 내면 안 된다 — `Net-(U3-LNA_IN)` 은 원래 그 이름이다.
  이걸 안 갈랐다가 멀쩡한 이름 21개를 "잘렸을 수 있다"고 말할 뻔했다

### 부품번호는 이제 두 길로 온다 (8/20 이음)

`mpn.py` 가 **어디서 알았는지까지** 들고 다닌다 (`PartNumber.source` = `bom` | `schematic`).

- **BOM 이 먼저다** — 사람이 직접 적은 것이 도구가 자동으로 채운 것보다 세다.
  회로도는 BOM 이 없거나 BOM 이 빠뜨린 부품을 채운다
- 사실 DB 조회(`runner._lookup_facts`) · 칩 판정(`chip_of`) · 해제 경로(`_clearance.ask`) ·
  `parts_identified` 가 전부 이 한 자리를 본다
- **BOM 없이 회로도만으로 데이터시트 해제가 난다** — 확인했다
- 끊긴 자리마다 **고칠 곳을 말한다.** BOM 을 낸 사람에게 "BOM 을 내세요" 는 거짓말이고,
  회로도로 올린 사람에게 "BOM 을 내세요" 는 유일한 길이 아니다

## 6. 현재 실제 상태

없는 것을 있다고 가정하지 않도록 정확히 적는다. **변경 시 이 절을 갱신할 것.**

### 있다 (동작 확인됨)
- `src/prefab` 패키지 — `_incoming/` 프로토타입 이식 완료.
  이식 전후 JSON 이 **바이트 단위로 같다** (규칙 개수 정정분 제외)
- IPC-D-356 파서 — 실제 보드에서 네트 8 / 부품 10 정확히 추출.
  좌표는 오프셋이 아니라 정규식 `X([+-]\d{6})Y([+-]\d{6})` 로 읽는다
- **회로도 넷리스트 파서** (`netlist/kicadxml.py`) — `kicad-cli sch export netlist --format kicadxml`
  결과를 읽는다. **핀 이름이 안 잘리고 부품번호·데이터시트 URL 이 함께 온다.**
  `Pad.name` 이 그 이름이고, 없으면 `None` 이다 (지어내지 않는다).
  심볼이 붙여둔 핀번호 접미(`GPIO3_8`)는 **번호와 정확히 맞을 때만** 뗀다
- **형식 감지** (`netlist/detect.py`) — `parse_any()` 가 내용의 첫 글자로 파서를 고른다.
  XML 로 보이는데 kicadxml 이 아니면 d356 으로 **안 되돌린다** — 그러면 엉뚱한 오류가 나서
  사용자가 진짜 원인을 못 찾는다
- 규칙 엔진 — **카탈로그 14개 전부 동작 (14/14).**
  R10 은 이전 넷리스트를 **선택 입력**으로 받는다 (`ctx.git`) — `datasheet` 와 같은 자리다.
  계약 어휘를 넓히지 않았다: 웹으로 파일 셋을 올리는 사람에게는 이전 상태가 없고, 있는 곳은 CI 다
- **데이터시트 해제 경로** (`rules/_clearance.py`) — R11 · R12 가 사실 DB 를 보고
  경고를 **해제(`PASS`)하거나 확정(`FAIL`)**한다. 비교는 결정적 코드가 한다.
  해제에는 **반드시 출처(`Evidence.datasheet`)가 붙는다.**
  못 풀면 **무엇이 있으면 풀리는지**를 적는다 — "BOM 필요"는 BOM 을 낸 사람에게 거짓말이다.
  **질문이 틀린 경우도 막는다**: 도메인을 추론으로만 아는 부품은 이 네트를 구동하는지도
  모르므로 `Voh` 를 알아도 해제하지 않는다 (K1 이 이 경우다)
- 규칙 카탈로그 (`catalog.py`) — 규칙 개수의 **유일한 진실**.
  `GET /rules` 와 `summary.rules_*` 가 전부 여기서 계산된다
- FastAPI (`web/app.py`) — 엔드포인트 4개 + CORS. 로직은 `web/service.py` 에 있다
- CLI — `python -m prefab <파일> [--json|--rules-json]` · `--facts-load` · `--facts`
- **BOM CSV 파서** (`bom.py`) — 부품기호·부품번호를 읽어 넷리스트와 맞춘다.
  도구별 열 이름 별칭 · 한 행에 여러 부품(`"C1,C2,C3"`) · 엑셀 CP949/BOM 인코딩을 처리한다.
  **양쪽 방향을 다 본다** — BOM 에 없는 부품, 번호가 빈 부품,
  그리고 **회로도에 없는 BOM 부품**(BOM↔회로도 어긋남)까지 보고한다
- **부품 사실 DB** (`datasheet/facts.py` · `datasheet/store.py`) — `checks` 와 **같은**
  SQLite 파일의 `part_facts` 표. 러너가 BOM 의 부품번호로 조회해 `Context.datasheet` 에 넣는다.
  **조회는 러너에서 끝난다** — 규칙 함수는 DB 를 모른다 (2-1).
  저장기가 두 가지를 거절한다: **값이 있는데 출처(page·quote)가 없는 것**,
  **값이 없는데 이유가 없는 것**. `value: null` + `reason` 은 정상적인 사실로 저장한다.
  `confidence: low` 는 저장은 되지만 `usable` 이 아니라 **판정에 못 쓴다**
- **보드 → 칩 매핑** (`part_aliases` 표) — BOM 에는 보드 이름이 적히고 데이터시트는
  칩 이름으로 나온다. 사실 파일의 `applies_to_boards` 가 그 둘을 잇는다.
  **핀 전기 특성만 물려받는다** (`facts.CHIP_INHERITED`) — `vcc_nominal` 은 뺐다.
  보드에는 레귤레이터가 있어서 (XIAO 는 USB 5V → 칩 3.3V) 칩 전압을 보드 전압이라고
  하면 틀린 값으로 R11·R12 가 판정한다. 보드가 직접 가진 사실이 칩 것보다 세다
- **사실 파일 CLI** — `python -m prefab --facts-load parts/*.json`.
  **LLM 없이 사람이 데이터시트를 읽고 채울 수 있다.** 서식과 규칙은 `parts/README.md`
- **데이터시트 LLM 추출** (`datasheet/extract.py` · `datasheet/pdf.py`) —
  PDF 를 쪽별로 읽어 LLM 에 넘기고, 스키마를 강제해 사실을 받는다.
  **그 다음이 핵심이다: 모델이 댄 인용문이 그 쪽 원문에 정말 있는지 코드가 대조한다.**
  없으면 버린다. 지어낸 출처가 DB 에 들어가는 걸 막을 수 있는 자리는 여기뿐이다
  (저장기는 출처가 "있어" 보이면 받는다).
  `python -m prefab --extract <pdf> --mpn X --source-url ... > parts/x.json`
  결과는 DB 가 아니라 **파일로 나온다** — 사람이 보고 커밋할지 정한 뒤에 들어간다
- **실제 LLM 호출 — 됐다 (8/19).** `--extract` 로 `HLK-LD2410C` 매뉴얼 5쪽을 돌려
  사실 8건을 뽑았고 원문 대조 탈락 0건이었다. 비용 약 $0.03.
  **그 결과가 사람이 손으로 넣은 값을 반박했다** — 아래 `io_level` 참고
- **`parts/hlk-ld2410c.json`** — 제조사 공식 PDF 17쪽 Table 2 에서 읽은 실제 값.
  이것 하나로 실측 보드의 `PRESENCE_3V3` 경고 **2건이 해제된다** (치명 4·경고 2 → 치명 3·경고 1·해제 2).
  `prefab.db` 는 `.gitignore` 라서 **커밋되는 진실은 이 JSON 뿐이고**,
  `tests/test_parts_files.py` 가 이 파일만으로 실제 해제가 나는지 검증한다
- **발견 합치기** (`engine.dedupe`) — 같은 네트에서 **새로운 근거를 하나도 못 내놓는**
  발견을 합친다. R11 은 R12 와 근거가 같은 넷리스트 줄이라 합쳐진다.
  **심각도로 고르면 안 된다** — 그렇게 만들었더니 차별 등급 R08 이 기본 등급 R12 에
  먹혀 사라졌다. 기준은 근거다. 합쳐진 규칙은 남은 발견의 `suggestion` 에 적힌다
- **검증 측정** (`measure.py` · `tests/fixtures/injected/`) — 라벨된 케이스에 엔진을
  돌려 검출율·오탐율을 낸다. `python -m prefab --measure`.
  **결함 없는 케이스가 오탐율의 전부다** — 겉모습이 비슷한데 정상인 보드를 짝으로 둔다.
  케이스를 못 읽으면 숫자에서 조용히 빼지 않고 그대로 적고 종료 코드 1 로 끝낸다.
  보고서가 **무엇을 못 재는지도 같이 적는다** — 숫자만 떼어 인용되면 안 된다
- **커밋 간 드리프트 검사** (`diff.py` · `.github/workflows/drift.yml`) — **F-1.**
  PR 마다 **같은 엔진(HEAD 코드)** 을 base 입력과 head 입력에 각각 돌려 발견 목록을
  비교하고, 새로 생긴 치명 발견이 있으면 빨간불로 막는다. R10 을 기다리지 않고도
  드리프트 서사가 완성되는 자리다 (`결정_기록.md` D-2).
  `python -m prefab --diff before.json after.json --fail-on-new`.
  **base 코드로 base 입력을 돌리면 안 된다** — 규칙을 고친 것과 보드를 고친 것이
  섞여서, 규칙을 추가한 PR 이 "보드가 나빠졌다"로 읽힌다. 워크플로가 그 순서를 지킨다.

### 배운 것 — `voh_max` 와 `io_level` 은 다르다

사람이 `HLK-LD2410C` 의 "IO level 3.3V" 를 `voh_max` 로 적었다. **매뉴얼에 Voh 규격
표는 없다.** LLM 추출이 그걸 잡아내고 `null` 을 돌려주며 "IO 레벨 표기이지 Voh
규격값이 아니다" 라고 적었다. 사람 쪽이 헌법 2-2 를 어긴 것이었다.

항목을 나눴다. `io_level` 은 모듈 IO 가 도는 로직 레벨이고, 규칙은 `voh_max` 를
먼저 보되 없으면 `io_level` 로도 판정한다 (IO 레일이 3.3V 면 그 핀 출력이 5V 로
올라갈 수 없다). 근거 문구도 "IO 로직 레벨"이라고 정확히 말한다.

**모듈 데이터시트는 Voh 규격을 잘 안 준다.** 다음 부품에서도 같은 일이 생긴다.

### 배운 것 — 해제는 되돌릴 수 있어야 한다 (8/21)

**이 프로젝트에서 제일 값진 한 건이다.**

1. R12 가 `_IN_ACTIVE_LOW` 를 짚었다 — 5V 릴레이가 3.3V MCU 와 같은 네트다
2. 하드웨어 담당이 모듈을 뽑아 IN↔VCC 를 20kΩ·2MΩ 로 쟀고 둘 다 OL 이었다.
   `input_pullup_to: none` 으로 저장했고 **경고가 해제됐다**
3. 그때 그 사실 파일에 이렇게 적어 뒀다 —
   *"저항계는 트랜지스터·다이오드 경로를 못 보므로 '저항성 풀업이 없다' 까지가
   이 측정이 말하는 전부다."*
4. **보드가 그 자리에서 고장 났다.** "LED가 ON은 되는데 OFF가 안된다" —
   3.3V 가 K1 의 입력 문턱에 못 미쳤다
5. `io_level: 5V` 를 실측으로 넣었고, 그 네트는 **해제에서 R04 치명으로 돌아섰다**

**적어둔 한계가 그대로 왔다.** 그리고 앞의 측정은 *틀린 값이 아니라 좁은 값*이었다 —
저항성 풀업이 없다는 것은 지금도 사실이고, 그것만으로 "5V 가 올라올 길이 없다" 가
안 나온다는 것을 알게 됐을 뿐이다. **한 번 지운 것을 영영 못 되살리면 그건
파이프라인이 아니라 예외 목록이다.**

REV2(2N3904 레벨시프트)에서는 R04·R15 가 **둘 다 조용해진다** —
`tests/test_rev2_transistor_fix.py` 가 그 고리를 붙잡는다.

4. ~~**R12 근거 문구가 신호 방향을 단정한다.**~~ **고쳤다 (8/18).**
   도메인을 추론으로만 아는 부품에는 "직결되어 있습니다"라고만 쓰고 방향을 말하지 않는다.
   해제 경로도 같이 막았다 — 구동하는 쪽인지 모르면 `Voh` 는 물어볼 값이 아니라서
   사실이 있어도 해제하지 않는다.
   **남은 것**: 핀 방향을 실제로 알아내는 길이 없다. `_IN_ACTIVE_LOW` 의 K1 은
   `input_pullup_to` 로 풀리는데, 그러려면 규칙이 어느 쪽이 입력인지 알아야 한다.
   지금은 "핀 방향과 내부 풀업을 확인해야 합니다"로 사용자에게 넘긴다.

## 7-1. 규칙 발견 (`discover/`) — 판정이 아니다

**우리 규칙이 못 본 것을 찾아 후보로 올린다.** `rules/` 와 폴더를 나눈 이유가 그것이다.

    rules/      판정한다.  Finding.    검사 결과에 들어간다.  LLM 안 부른다
    discover/   제안한다.  Candidate.  사람이 채택해야 규칙이 된다

**근거가 있는 설계다.** 같은 케이스를 LLM 에 던졌더니 합성에서는 우리가 이겼는데
남의 실보드에서는 졌고(LLM 오탐 0 · 우리 45), LLM 이 지적한 것 하나가 **진짜 결함**이었다.
우리 규칙 12개 중 어느 것도 그 모양을 안 보고 있었고 그게 R14 가 됐다.
그때 사람이 손으로 한 일을 제품이 하게 만든 것이다.

    LLM 이 제안한다  →  **코드가 검증한다**  →  사람이 채택한다

가운데가 이 모듈의 존재 이유다. `verify.py` 는 **순수 함수**이고 네 가지를 본다 —
자리가 실재하는가 · 인용이 원문과 맞는가 · 이미 규칙이 보고 있는가 · 말이 되는가.

**만들면서 데인 것 셋.**

- 출력 상한을 4000 으로 뒀더니 모델이 그걸 전부 생각에 쓰고 답을 못 냈다.
  블록이 `thinking` 하나뿐이라 "응답에 본문이 없습니다" 라는 엉뚱한 사유가 나왔다
- 응답 text 블록을 **이어붙였다.** 첫 블록 하나가 곧 JSON 이다 (`extract.py` 와 같은 규칙)
- 모델이 `where` 에 `main.ino:13` 처럼 합쳐 냈는데 파일명으로만 찾아서
  **쓸 만한 후보 넷을 통째로 버렸다.** 형식이 어긋난 것과 지어낸 것은 다르다 —
  거르려는 것은 지어낸 *내용*이지 표기법이 아니다

**입력이 상한을 넘으면 자르지 않고 안 묻는다.** 조용히 자르면 모델이 못 본 파일에 대해
"문제 없음" 처럼 답하게 된다. 실측 보드 6개 중 2개가 상한을 넘는다.

기본은 꺼져 있다 — `python -m prefab <넷리스트> --discover`.

## 11. 근거 문구 규약 (8/19 추가)

발견의 `claim` · `evidence` 는 **사용자에게 그대로 노출된다.** 판정이 맞아도 문구가 틀리면
도구 신뢰가 끝난다. 실제로 한 번 났다 — 풀다운 저항을 "pull-up" 이라고 적고 있었다.

- **단정하지 않는다.** 넷리스트가 말해 주지 않는 것은 쓰지 않는다.
  누가 누구를 구동하는지는 핀 이름이 출력이라고 말할 때만 쓴다 (`pad-` 는 모른다).
- **반대쪽을 본다.** 네트에 붙은 저항은 반대쪽 터미널로 풀업/풀다운/분기를 가른다.
- **발췌를 지어내지 않는다.** `snippet` 은 파일에 실제로 있는 줄 그대로다.
  주석을 덧붙이지 않는다. 사용자가 그 줄을 열어본다.
- **가리킬 줄이 없으면 `line: null`.** R08 처럼 부재가 근거인 경우다. `line: 1` 을 넣지 않는다.
- **확정된 패드는 실크 라벨로 쓴다.** `U1.SDIO` 는 D3·D4·D5 중 무엇인지 말해 주지 않는다.
- **조사를 맞춘다.** `text.py` 의 `eun` · `i_ga` · `eul` · `gwa` 를 쓴다.

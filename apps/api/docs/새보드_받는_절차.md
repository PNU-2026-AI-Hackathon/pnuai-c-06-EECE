# 새 보드를 받으면 — 절차

회로도가 도착한 날 **반나절 안에** 끝내기 위한 순서다.
백엔드_요청서 4절 1순위의 세 줄을 실제로 돌 수 있게 풀어 쓴 것.

---

## 0. 받기 전에 — 하드웨어 담당에게 보낼 한 줄

**PCB 를 안 떠도 넷리스트가 나온다.** 이 전제가 한 번 틀리게 공유됐다.

```bash
kicad-cli sch export netlist --format kicadxml -o board.xml board.kicad_sch
```

회로도 파일 하나면 된다. 그리고 **이쪽이 정보가 더 많다** —
IPC-D-356 은 부품번호를 0% 싣지만 kicadxml 은 100% 싣는다.

같이 받아야 하는 것:

| | 왜 |
|---|---|
| 넷리스트 (`.xml` 또는 `.d356`) | 필수 |
| 펌웨어 소스 | **차별 규칙 6개가 전부 이것을 필요로 한다.** 없으면 기본 규칙만 돈다 |
| BOM CSV | kicadxml 이면 없어도 된다 (회로도가 부품번호를 실어 준다) |

## 1. 픽스처로 추가한다 — **옛 보드를 덮지 않는다**

```bash
cp <받은파일> apps/api/tests/fixtures/<보드이름>.net.xml
```

**기존 픽스처를 고치지 않는다.** 골든 테스트 · 측정 기준선 · 샘플 검사가 전부
그 위에 서 있다. 새 보드는 **픽스처가 하나 더 생기는 것**이다.

바로 한 번 돌려서 파서가 읽는지부터 본다:

```bash
cd apps/api
PYTHONPATH=src .venv/bin/python -m prefab tests/fixtures/<보드이름>.net.xml
```

읽히면 2번으로. 안 읽히면 **거기서 멈춘다** — 파서 문제를 정답표보다 먼저 푼다.

---

## 2. `EXPECTED.md` 를 손으로 쓴다

```bash
cp tests/fixtures/EXPECTED.template.md tests/fixtures/<보드이름>.EXPECTED.md
```

**엔진 출력을 베껴 넣지 않는다.** 그러면 엔진이 틀렸을 때 정답표도 같이 틀려서
골든 테스트가 아무것도 안 지킨다. 회로도를 보고 사람이 판단해서 적는다.

순서:

1. 회로도를 열고 **어떤 어긋남이 있어야 하는지** 먼저 적는다
2. 그다음에 엔진을 돌린다
3. 둘이 다르면 **어느 쪽이 틀렸는지 판정한다** — 엔진일 수도, 내 예상일 수도 있다

3번이 이 문서의 값어치다. 순서를 바꾸면 그 판정이 사라진다.

## 3. 0건이면 왜 0건인지 확인한다

> **"이상 없음"과 "못 봤음"은 다르다.**

```bash
PYTHONPATH=src .venv/bin/python -m prefab tests/fixtures/<보드이름>.net.xml \
  --firmware <fw/> --bom <bom.csv> --why
```

`--why` 가 세 가지를 말한다.

| | |
|---|---|
| **재료** | 넷리스트 · 좌표 · 부품번호 · 칩 · 핀맵 · 펌웨어 · 부품 사실 |
| **조용한 규칙** | 돌긴 돌았는데 아무 말도 못 한 규칙과 짐작되는 사유 |
| **오탐이 늘 수 있는 자리** | 재료가 없어서 억제가 안 되는 규칙 (방향이 반대다) |

마지막 줄이 결론을 내려 준다:

```
발견 0건이고 **재료가 다 갖춰져 있다.** 이 0건은 '이상 없음' 이다.
```
```
발견 0건이지만 **'이상 없음'이 아니다.** 없는 재료: 칩 식별 · 펌웨어.
이 상태의 0건은 '못 봤음' 에 가깝다 — 위 목록을 채우고 다시 돌려야 한다.
```

**두 번째가 나오면 픽스처를 확정하지 않는다.** 재료를 먼저 채운다.

가장 흔한 두 가지:

- **칩 식별 ❌** → 부품번호가 없다. BOM 을 받거나 회로도 심볼에 MPN 을 채워야 한다.
  R01·R02·R03·R05·R09 **다섯 개가 통째로 침묵한다**
- **펌웨어 ❌** → 차별 규칙 6개가 건너뛰어진다. **우리 차별점이 화면에 안 나온다**

## 4. 정답표를 테스트로 고정한다

`tests/test_golden_real_board.py` 를 본떠 새 파일을 만든다.
`EXPECTED.md` 의 숫자가 바뀌면 테스트도 같이 바뀐다 — **문서가 먼저다.**

---

## 5. 측정 데이터셋에 넣는다

```python
# scripts/make_injected.py 의 REAL_BOARD 옆에
{
    "id": "real-<보드이름>",
    "kind": "실측",
    "expect": [...],          # EXPECTED.md 3절과 같아야 한다
    "netlist": "../<보드이름>.net.xml",
}
```

```bash
python scripts/make_injected.py && PYTHONPATH=src .venv/bin/python -m prefab --measure
```

**실측 케이스가 늘어나는 것이 이 데이터셋에서 가장 값진 변화다.** 합성은 우리가
만든 상황이고, 실측만이 "우리가 만들지 않은 상황"이다.

---

## 6. 프론트 목 데이터를 다시 뽑는다

엔진 출력이 바뀌면 화면이 옛 결과를 보여준다.

```bash
PREFAB_DB=/tmp/empty.db PYTHONPATH=src .venv/bin/python -m prefab <인자> --json \
  > ../web/src/mocks/check.json
PYTHONPATH=src .venv/bin/python -m prefab --rules-json > ../web/src/mocks/rules.json
```

`PREFAB_DB` 를 빈 파일로 두는 이유는 로컬 사실 DB 가 섞이면 커밋된 파일만으로
재현이 안 되기 때문이다.
